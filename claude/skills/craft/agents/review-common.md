# レビュー系エージェント共通ルール

verify・security-reviewer・qa・code-reviewer・adversarial-reviewer に共通する規則。
build フローのステップ5で、メインが内容を各依頼文に貼り込む（貼り込まれていない場合は、依頼文で示された絶対パスを Read する）。

## 担当範囲（排他）

自分の担当外の指摘はしない。他のレビューが別に見ているため、重複は triage の負担になる。
各エージェントの「担当範囲」の記述（各 agents/<name>.md）を正とする。次の表はその要約で、食い違う場合は各エージェントの記述に従う。

| エージェント | 担当 | 担当外の例 |
|---|---|---|
| verify | 要件・受け入れ条件との照合 | コード品質、脅威、テストの質 |
| security-reviewer | 脅威、入力、秘密情報、依存・サプライチェーン | 要件の過不足、テストの有無 |
| qa | テストの有無・網羅、異常系の画面表示 | 脅威、構造、要件の過不足 |
| code-reviewer | 構造、並行性、エラー処理、規約 | 脅威、テストの網羅、要件の過不足 |
| adversarial-reviewer | 壊す側の筋書き（暗号・OS 権限・配布のとき） | スタイル、命名、構造の好み |

担当が重なる観点は、報告者を1つに決める。脅威の観点は security-reviewer、実装の欠陥は code-reviewer、
複数の欠陥を組み合わせた筋書きは adversarial-reviewer が報告し、他は触れない。
ただし security-reviewer が実行されない場合（レビュートラックに含まれない場合）は、code-reviewer が脅威の観点も担当する。

## 出力の形式

「指摘事項」の部分は、次の表にまとめる。サマリー・カバレッジ表・走査確認・判定など、各エージェント固有の節は、
各エージェントの出力フォーマットに従う。固有の項目（確信度など）は、表の末尾に列を追加してよい。

| ID | 重要度 | 場所 | 内容と根拠 | 修正案 |
|---|---|---|---|---|

- ID は担当の頭文字＋連番。頭文字: verify=V、security-reviewer=S、qa=Q、code-reviewer=C、adversarial-reviewer=A（例: S-1）。
- 重要度は 高 / 中 / 低。エージェントごとの呼称は次に対応させる: 重大=高、中程度=中、軽微=低。
- 高・中は全件を表にする。
- **低は表にしない。** 件数と代表例（最大2件）だけを書く。
  コメントの質・テストの題名・命名のように、機械的に直せるものは、別枠「機械的に直せるもの」に件数だけ書く。
- 修正案には、修正コードを書かない。
- 「機械的に直せるもの: N 件」の1行は、各エージェントの「低」の節の末尾に書く。
- 要件表やカバレッジ表を本体とするエージェント（verify、qa）は、その表を維持し、ズレ・不足の項目だけを指摘とみなして ID を付ける。
  重要度の対応: 未実装・必須の不足テスト=高、部分実装・技術選定の乖離=中、推奨の不足テスト=低。
  「確認不能」は「未確認」として別記する。

## 判定の区分

各エージェントの判定語を、次の3区分に対応させる。build フローのステップ5は、この区分で分岐する。

| 区分 | 判定語の例 |
|---|---|
| 承認 | 承認、承認（任意の指摘あり） |
| 条件つき承認 | 必須テスト追加後に承認、軽微な修正後に承認、承認（リリース前に対応推奨） |
| 要対応 | 要対応、要修正、重大問題あり・要修正、非承認 |

## 事実の扱い

- 実行していない項目、確認できなかった項目は、断定せず「未確認」と書く。
- メインが実行済みのテスト・lint の結果は、再実行しない。ただし、実行しないと確かめられない指摘
  （テストの有無・通過を主張する場合など）に限り、対象を絞って実行してよい（ファイルの変更は禁止）。
