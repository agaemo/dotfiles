# /craft

システム開発に関する作業を開始する。

## 実行時の一般原則（craft 配下の全フロー・全エージェントに適用）

IMPORTANT: **内部変数名をユーザーに見せない。** `STACK`・`HAS_FRONTEND`・`HAS_REVIEW_CHAIN` 等の
制御変数は、進捗報告・完了報告・確認メッセージなどユーザー向けの出力に変数名のまま
含めないこと。「HAS_FRONTEND=true のため〜」ではなく「フロントエンドがあるため〜」のように、
常に人間が読める言葉に変換してから伝える。

IMPORTANT: **`flows/*/SKILL.md`（scope・new-project・new-static・new-app・build 等）は
独立したスキルとして登録されていない。** Skill ツールでは呼び出せない（`Skill(craft:scope)` のような
呼び出しは存在しないスキルを呼ぶエラーになる）。必ず Read ツールでファイルを読み込み、
その内容に従って自分自身（メインClaude、または現在実行中のエージェント）が直接実行すること
（本ファイル内で「READ ... FOLLOW」と書かれている箇所はすべてこのパターン）。

IMPORTANT: **未知のツールを新規に導入する際は、実行前に公式ドキュメントを確認する。**
動作確認できたことと、公式に推奨された正しい手順であることは別。WebSearch/WebFetchで
公式のインストール手順を確認してから実行し、確認していない場合はその旨をユーザーに伝える。
この確認は自分から能動的に選んだツールに限らない。**scaffoldコマンドが自動的に持ち込む
中核的な依存関係（生成物のビルド・実行に不可欠なもの。例: ビルドツール本体・devサーバー・
フレームワーク本体。個々のUIコンポーネントやユーティリティ等の周辺ライブラリは対象外）も対象。**
scaffold直後にそれらのバージョンを確認し、1.0未満のベータ版・実験的リリースが含まれる場合は、
その旨と既知の制約をユーザーに伝えてから先に進む（気づかず使い続けない）。

IMPORTANT: **scaffold・生成系コマンドを対象ディレクトリで直接実行する前に、そのディレクトリに
`.craft/`・`.gitignore` 等の管理ファイルが既に存在する場合は、一時退避してから実行し、
生成完了後に復元・マージすること。** 多くのscaffoldツールは「ディレクトリが空でない」ことを
既存プロジェクトとみなして拒否・エラーにするため、craft自身が作った管理ファイルが誤判定の
原因になりうる。復元時にscaffoldが同名ファイル（`.gitignore`等）を新規生成していた場合は、
両方の内容を残す形でマージする（craft側のエントリを追記し、scaffold側の記述を削らない）。
また、生成コマンドの引数仕様（カレントディレクトリを指定できるか、force相当の挙動、既存ファイルが
ある場合の扱い等）は言語・ツール・バージョンによって異なるため、本番の対象ディレクトリに影響が
出る前に、一時ディレクトリ等で軽く試してから本実行すること。

IMPORTANT: **コンテナ（Docker等）で環境構築する場合、プロジェクト生成に使うツールチェーン
（一時コンテナ等）のバージョンと、実際にアプリを実行する環境（本番相当コンテナ）のバージョンを
一致させること。** 一致させる際は実行環境（本番相当コンテナ）側のバージョンを基準にし、
生成に使うツールチェーンをそれに合わせる（実行環境は要件・デプロイ先の制約で決まっていることが
多く、後から変えにくいため）。言語ランタイムのバージョンが生成時と実行時で異なると、依存関係の
ロックファイルに実行環境と互換性のないバージョン制約が書き込まれ、後になって競合が発覚する
（生成に使ったイメージのランタイムが実行環境より新しく、実行環境未対応のパッケージバージョンで
ロックされる、等）。

IMPORTANT: **フローの前提（技術スタック等）が崩れ、スキルの手順（plan.md等の進行管理を含む）から
外れて独自進行に切り替える場合は、その旨を即座にユーザーに明示してから続行する。** 黙って
スキルの管理下から外れない。

IMPORTANT: **技術スタック（言語・フレームワーク等）を途中で切り替える場合、旧スタックの
ビルド成果物（Dockerイメージ・コンテナ・ボリューム、インストール済みツールチェーン等）が
残存する。** 切り替えの計画を提示する際に、それらを削除するかどうかをユーザーに確認する
項目を含めること。確認せずに放置しない（残置するとディスク容量を圧迫し、後から見て
どちらのスタックの成果物か紛らわしくなる）。

## 手順

### ステップ 0: 種別選択

```
SKILL_DIR = このSKILL.mdが存在するディレクトリの絶対パス
  # 例: /Users/alice/.claude/skills/craft
  # このファイルを読んだパスから導出すること

IF .craft/docs/plan.md が存在する:
  # plan.md は初期設計ドキュメント。「既存実装の再開」か「新しい要件」かを明示的に確認する
  GATE: 「.craft/docs/plan.mdが見つかりました。今回の依頼はどちらですか？」とユーザーに確認する
    選択肢:
      1. plan.md の実装を続ける（中断した実装の再開）
      2. plan.md とは別の新しい要件として進める（fix ファイルを新規作成）
  WAIT_FOR: ユーザーの選択
  IF ユーザーが 1（再開）を選択:
    FOLLOW: 実装再開フロー（本ファイルの「## 実装再開フロー」セクション）
    STOP: 以降のステップは実行しない
  ELSE:
    # 新しい要件として扱う（fix ファイルの作成・plan.md への追記は consult フローの
    # ステップ4で行われる。ここでは何もしない）
    CONTINUE: 下記のscope読み込みへ進む
  ENDIF
ENDIF
# .craft/docs/plan.md がそもそも存在しない場合も、そのまま下記のscope読み込みへ継続する

READ {SKILL_DIR}/flows/scope/SKILL.md
IF READ FAILED:
  REPORT: "フローファイルが見つかりません: {SKILL_DIR}/flows/scope/SKILL.md。SKILL_DIR の導出を確認してください。"
  STOP
FOLLOW: そこに記述されたすべての手順を実行する
  NOTE: 種別の推定・確認・new-static/new-project/new-app/consult への振り分けは
        すべて scope フロー側で行われる。
STOP: 以降のステップは実行しない

```

NOTE: FOLLOW 実行中にエラーや予期しない STOP が発生した場合は、中断した箇所と理由をユーザーに伝え、
  再試行するか確認すること。選択肢は失敗した文脈に応じて提示する:
  - scope フロー（または委譲先フロー）の失敗時: 同じ種別を選択 / 別の種別を選ぶ / 中止する
  - 実装再開フロー（build フロー）の失敗時: 再試行する / 再開を中止する

## 実装再開フロー

（本セクションはステップ0の分岐からのみ到達する。SKILL_DIR はステップ0で定義済みの値をそのまま使う）

`.craft/docs/plan.md` が存在する状態から実装を続ける場合は、build フローに委譲する。
初回実装（各 new-xxx フローの設計完了後）と同じエンジンを使うため、手順の二重管理がない。

```
READ {SKILL_DIR}/flows/build/SKILL.md
IF READ FAILED:
  REPORT: "フローファイルが見つかりません: {SKILL_DIR}/flows/build/SKILL.md。SKILL_DIR の導出を確認してください。"
  STOP
FOLLOW: そこに記述されたすべての手順を実行する
  NOTE: STACK・HAS_REVIEW_CHAIN・HAS_FRONTEND は呼び出し元変数が無いため
        build フロー内で自動判定される（pubspec.yaml・design-brief.md 等の有無から推定。
        判定ロジックの詳細は {SKILL_DIR}/flows/build/SKILL.md の AUTO-DETECT を参照）
```
