# データストア選定ガイドライン

## 適用場面

- 新規プロジェクトでDBを使う場合の、DBエンジン選定
- キャッシュ/セッションストア（Redis等）を入れるかどうかの判断

「本番クラウド公開を今回行うか」とは独立した判断軸。個人開発・PoCの段階でも該当する。

---

## DBエンジンの選定

| エンジン | 向いているケース |
|---|---|
| SQLite | 個人開発・小規模・単一プロセス。同時書き込みが少なく、ファイル1つで運用したい |
| PostgreSQL | 迷ったらこちら。JSON型・全文検索・GIS拡張などの豊富な機能、拡張性、エコシステムの広さ |
| MySQL | 既存チームにMySQL運用実績がある、または利用予定のマネージドサービス側の制約がある場合 |

迷ったらPostgreSQLを選ぶ。SQLiteを選ぶ場合、「後からPostgreSQLへ移行する前提のPoCか」を
明示しておくと、後の移行コスト見積もりがしやすい。

---

## キャッシュ/セッションストア（Redis等）の要否

個人開発・単一プロセスの段階では、フレームワーク標準のセッション機構（DBセッション・
署名付きCookie）で足りることが多い。以下のいずれかに当てはまる場合のみ、Redis等の
導入を検討する：

- 複数インスタンス/プロセスでセッションを共有する必要がある（プロセスローカルの
  メモリセッションは複数台で共有できないため）
- 認証フレームワークがRedisセッションバックエンドを標準/前提としている
  （例：Django + django-redis）
- レート制限・ジョブキューなど、DB/インメモリでは実現しづらい機能を使う
- DB負荷軽減のための高頻度アクセスキャッシュが必要

いずれにも当てはまらない場合、個人開発の段階でRedisを入れる必要はない（過剰設計）。

導入する場合、Docker Compose段階では `docker-compose.yml` にRedisコンテナを1つ
追加するだけで済む。本番クラウド公開時はマネージドサービス（AWS ElastiCache /
GCP Memorystore）に置き換える、という環境ごとの実装差し替えは `agents/planner.md`
の「環境切り替え戦略の選定」の抽象化パターンに従う。
