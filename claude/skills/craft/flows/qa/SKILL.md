---
name: qa
description: 既存プロジェクトのQA基盤を構築する。テスト方針の策定・フレームワーク導入・優先順位付けによる段階的なテスト実装・CI組み込みまでを一貫して進める。
---

# qa（QA基盤構築フロー）

テストが少ない・ない既存プロジェクトに、QA基盤を一から作る。
「何をどの順で書くか」の戦略を立ててから実装に入る。

---

## 手順

### ステップ 1: ブリーフィング

```
IF consult または qa-consult から SUMMARY（ここまでの相談内容の要約）が渡されている:
  USE: SUMMARY を現状の説明として使う（同じ内容を聞き直さない）
ELSE:
  ASK USER:
    現在のテスト状況と困っていることを教えてください。

    例:
    - テストがほぼない状態で、どこから始めればよいかわからない
    - 一部はあるが、重要な箇所が抜けている
    - テストはあるが壊れやすく保守できていない

  WAIT_FOR: ユーザーの説明

ASK: 不足している点のみ1件ずつ追加質問する
  - 使用している言語・フレームワーク
  - 既存のテストフレームワーク（あれば）
  - CI/CDの有無
  - 特に不安な箇所（認証・決済・データ処理など）
  - 追加したい範囲（対象の機能・画面、本数の目安。ステップ2.5の軽量経路の判定に使う）
```

### ステップ 2: 現状調査

```
READ: コードベースを調査し以下を把握する

  --- テストの現状 ---
  - 既存テストファイルの有無・場所
  - テストフレームワークの設定（package.json / pyproject.toml 等）
  - カバレッジ計測の設定有無
  - テスト実行の事前条件（サーバー起動・環境変数・テストデータ。CLAUDE.md / README を参照して確認する）
  RUN: カバレッジ計測コマンドが設定されていれば実行する

  --- リスク評価 ---
  - 認証・認可・決済・データ整合性に関わるファイル
  - 複雑度の高い関数（行数・分岐数）
  - 変更頻度の高いファイル:
    RUN: git log --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20

  --- テスタビリティ ---
  - 依存注入・モックが困難な箇所（グローバル状態・密結合）
  - 外部サービス依存（DB・API・メール等）

REPORT: 調査結果をユーザーに提示
  - 現在のカバレッジ率（計測できた場合）
  - リスクの高い未テスト箇所トップ10
  - テスタビリティの懸念点（対象ファイルごとに ○=懸念なし / ×=DI・モック困難・グローバル状態・密結合・外部依存直結 を判定して記録する）
```

### ステップ 2.5: 軽量経路の判定

```
IF 次の両方を満たす:
  - 追加したい種別のテストフレームワークが、既に導入・設定済みである
  - 依頼が特定の機能・画面・対象へのテスト追加（数本程度）に限られ、
    基盤整備や網羅的な拡充ではない
  PRESENT: 「既存のテスト基盤があり追加範囲も限られているため、QA基盤構築計画
            （フレームワーク選定・優先実装リスト・CI）は省略し、対象を決めて追加する
            軽量経路で進めます。通常の構築計画で進めたい場合はお知らせください」
  GATE: 軽量経路 / 通常経路 をユーザーに確認する
  IF 軽量経路:
    PLAN: 追加するテストの対象・種別・既存の命名規則とディレクトリ・実行コマンド・
          実行の事前条件・検証方法のみを簡潔に提示する（ステップ3の全体計画は作らない）
    GATE: 承認を得る
    読み替え:
      - ステップ3: 実行しない（上記 PLAN が代わりとなる）
      - ステップ4: そのまま実行する。ただし issue / PR のタイトルは
        「[qa] {対象}のテスト追加」、ブランチ名は「qa/{対象を表す短い名前}-tests」とする。
        質問文の「QA基盤構築の背景・方針を記録」は「テスト追加の背景・方針を記録」に、
        issue 本文の「方針」「優先実装リスト」は 2.5 で承認した PLAN の内容に読み替える
      - ステップ4.5: 実行しない（導入済みのため）
      - ステップ5: 優先実装リストの代わりに、承認した対象を処理する。
        「ステップ3で策定したモック方針・命名規則」は、2.5 の PLAN で確認した既存の規則に読み替える
      - ステップ6: PR のタイトル・本文の「QA基盤構築」を「{対象}のテスト追加」に読み替える。
        本文の「QA戦略」は 2.5 で承認した PLAN の内容に読み替える
  IF 通常経路:
    ステップ3へ進む
ELSE:
  # 条件を満たさない、または追加範囲が不明なままの場合
  ステップ3へ進む（通常経路）
```

### ステップ 3: QA戦略の策定・承認

NOTE: ステップ2.5 で軽量経路を選んだ場合は、このステップを実行しない。

```
PLAN:

  ## QA基盤構築計画

  ### テストフレームワーク
  [既存スタックに合わせて選定。すでに導入済みの場合はそのまま活用]
  - 単体・統合テスト: [例: Vitest / Jest / pytest]
  - E2E: [例: Playwright]（フロントエンドがある場合）
  - カバレッジ: [例: v8 / istanbul / coverage.py]

  ### テスト方針
  - カバレッジ目標: [現状 + 段階的な目標。最初から100%は目指さない]
  - テストの粒度: [単体・統合・E2Eの比率]
  - モック方針: [外部サービスのモック方法]
  - 命名規則・ディレクトリ構成

  ### 優先実装リスト（リスクベース）
  以下の基準でスコアリングして優先度を決める（加点が高い順に着手）:

  | 基準 | 加点 |
  |------|------|
  | バグ履歴がある（git log / issue で確認） | +3 |
  | 変更頻度が高い（ステップ2で上位） | +3 |
  | 認証・決済・DB書き込みなど高リスクな処理を含む | +2 |
  | テストゼロ | +2 |
  | 複雑度が高い（条件分岐・ネストが多い） | +1 |

  | 優先度 | 対象 | スコア | テスト種別 |
  |--------|------|--------|-----------|
  | 1      | ...  | ...    | ...        |
  | 2      | ...  | ...    | ...        |
  ...

  ### CI組み込み（任意）
  [GitHub Actions 等への組み込み案]

GATE: 戦略の承認を得る
  → 修正要望があれば更新して再提示する
PROHIBITED: 承認前にステップ4（準備）へ進むこと
```

### ステップ 4: 準備

```
# デフォルトブランチを最新化してからブランチを切る
DEFAULT_BRANCH = git symbolic-ref refs/remotes/origin/HEAD | sed 's@^refs/remotes/origin/@@'
RUN: git checkout {DEFAULT_BRANCH} && git pull
IF 失敗:
  REPORT: pull に失敗した旨を伝え、ユーザーの判断を仰ぐ
  STOP

ASK USER:
  作業にあたって以下を確認します。
  1. GitHub issue を作成しますか？（QA基盤構築の背景・方針を記録）
  2. 完了後に PR を作成しますか？

WAIT_FOR: ユーザーの回答

CREATE_ISSUE = ユーザーが issue 作成を希望した場合
CREATE_PR    = ユーザーが PR 作成を希望した場合

IF CREATE_ISSUE:
  gh issue create \
    --title "[qa] QA基盤構築" \
    --body "## 背景\n[ブリーフィングで把握した課題]\n\n## 方針\n[ステップ3で策定した戦略]\n\n## 優先実装リスト\n[対象一覧]"
  ISSUE_NUMBER = 作成した issue の番号
ELSE:
  ISSUE_NUMBER = なし

RUN: git checkout -b qa/bootstrap
```

### ステップ 4.5: 環境構築

```
IF テストフレームワークが未導入:
  EXECUTE: フレームワークのインストール・設定ファイル作成
    例: pnpm add -D vitest @vitest/coverage-v8
  VERIFY: テストコマンドが実行できること

IF カバレッジ計測が未設定:
  EXECUTE: カバレッジ設定を追加する

IF CI組み込みを希望:
  EXECUTE: GitHub Actions 等のワークフローファイルを作成する

GATE: 環境構築の完了を確認する
```

### ステップ 5: 段階的テスト実装

```
優先実装リストの順に、以下を繰り返す:

FOREACH target IN 優先実装リスト:
  REPORT: 「[対象] のテストを実装します」と通知

  IF target がテストゼロ、かつ ステップ2で記録した当該対象のテスタビリティ判定が「×」:
    FOLLOW: 下記「レガシーコードへの安全なテスト追加」
  ELSE:
    # tester は subagent_type として登録されていない。agents/tester.md の全文を
    # プロンプトに貼り込み、汎用サブエージェント（general-purpose 等）で起動する。
    # 非同期実行のため、完了通知が届くまで次の作業を進めない
    READ {SKILL_DIR}/agents/tester.md
    Agent（汎用サブエージェント）に tester.md の全文と以下を渡して起動:
      対象: [ファイル・関数]
      テスト種別: [単体 / 統合 / E2E]
      方針: [ステップ3で策定したモック方針・命名規則]
      事前条件: [ステップ2で確認したテスト実行の事前条件]
      重点: [境界値・異常系・ビジネスルール]

  IF tester から「事前条件が未達」と報告された（サーバー未起動など）:
    ユーザーに必要な手順を伝え、許可を得てから実行する（データを変更しうる操作は特に明示する）
    実行後、tester を再度起動して同じ対象を依頼する

  VERIFY: テストが通ること。ただし、カバレッジ計測が設定済みで対象が単体・統合テストの場合は
          カバレッジが上がっていることも確認する（E2E の場合や、計測が未設定の場合は確認しない）
  IF 失敗: 原因を報告し、tester エージェントを再呼び出しして修正してから次へ進む

  GATE: 次の対象に進む承認を得る
    → 現在地を確認する（カバレッジを計測できる場合はレポートを提示する）
```

#### レガシーコードへの安全なテスト追加

対象がこの手順に該当する場合のみ読み込む（Characterize → Seam の安全な進め方を定義）。

```
READ {SKILL_DIR}/flows/qa/legacy-testing.md
FOLLOW: そこに記述された STEP A〜C を実行する
```

### ステップ 6: 完了・PR 作成

```
IF CREATE_PR == false:
  REPORT: 完了レポートを表示して終了
  RUN: git checkout {DEFAULT_BRANCH}
  STOP

CREATE PR:
  タイトル: qa: QA基盤構築
  本文（以下をすべて記載すること）:

    ## 背景・課題
    [ブリーフィングで把握したテスト不足の状況と根本原因]

    ## QA戦略
    - テストフレームワーク: [名前・バージョン]
    - カバレッジ目標: [設定値]
    - モック方針: [内容]

    ## 構築したもの
    - テストフレームワーク導入: [有無・内容]
    - カバレッジ計測: [設定内容]
    - CI組み込み: [有無・内容]

    ## 実装したテスト
    | 対象 | テスト種別 | テスト数 |
    |------|-----------|---------|
    | ...  | ...       | ...     |

    ## カバレッジの変化
    - 開始時: X%
    - 完了時: Y%

    ## 今後の推奨事項
    - [ ] 次に実装すべきテスト（優先実装リストの残り）
    - [ ] 新規コードへのテスト必須化の方針
    - [ ] カバレッジ目標の次のステップ

    ## 確認方法
    [テストの実行コマンドとカバレッジレポートの確認手順]

    IF ISSUE_NUMBER != なし:
      Closes #ISSUE_NUMBER

  PR_NUMBER = 作成した PR の番号
  RUN /review {PR_NUMBER}
  IF レビューで重大な指摘がある:
    REPORT: 指摘内容をユーザーに共有し、対応するか確認する
    WAIT_FOR: ユーザーの判断

  RUN: git checkout {DEFAULT_BRANCH}
```
