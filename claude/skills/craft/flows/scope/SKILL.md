# scope（種別確認・技術カテゴリ選定フロー）

```
SKILL_DIR = このSKILL.md（craft/flows/scope/SKILL.md）のパスから2階層上の絶対パス
  # このファイルを /Users/alice/.claude/skills/craft/flows/scope/SKILL.md で読んだ場合
  #      → SKILL_DIR = /Users/alice/.claude/skills/craft
```

---

## 手順

### ステップ 1: 相談の入口

```
IF ここまでの会話の中で、何を作りたいか（概要）がすでに明確に語られている:
  SELF: その内容を「依頼の要約」として保持する（同じ内容を再度質問しない）
ELSE:
  ASK USER:
    何を作りたいか、または困っていることを自由に話してください。
  WAIT_FOR: ユーザーの話
  SELF: その内容を「依頼の要約」として保持する

ANALYZE: 「依頼の要約」を実際に理解した上で判断する。表面的なキーワードの有無だけで
  機械的に判定しない（例:「移行」「リファクタ」等の単語が無くても、既存のシステム・
  ツール・運用を出発点にした相談であれば既存相談として扱う）。
  IF 既存システムへの課題・移行・置き換え・リファクタ等、既存のものを出発点にした相談:
    READ {SKILL_DIR}/flows/consult/SKILL.md
    IF READ FAILED:
      REPORT: "フローファイルが見つかりません: {SKILL_DIR}/flows/consult/SKILL.md。SKILL_DIR の導出を確認してください。"
      STOP
    FOLLOW: そこに記述されたすべての手順を実行する
    STOP

# 新規構築と判断した場合のみ、ステップ2へ進む（キーワード一致による即断・委譲は行わない。
# 必ずステップ2のヒアリングを経てからステップ3で分類する）
```

### ステップ 2: 制約のヒアリング

```
ASK USER: 以下を1つのメッセージで教えてください
  1. 作りたいものは、公開・利用してもらうためのプロダクト（サイト/アプリ）ですか、
     それとも学習・検証のためのツール/サンプル/環境構築ですか？
  2. フロントエンドUI（画面）は必要ですか？（あり / なし）
  3. データの保存（DB）や認証は必要ですか？（あり / なし）
  4. 既存のエコシステムへの依存はありますか？
     （例: Google Workspace・Slack・既存のAWS/Firebase等。なければ「なし」）
  5. PoC・お試しですか、それとも継続的に運用しますか？
  6. 技術的な知識レベルはどの程度ですか？（自分でコードを書く / Claudeに任せたい）

WAIT_FOR: ユーザーの回答
```

### ステップ 3: カテゴリ対応表との照合

```
| 条件                                      | カテゴリ                | 状態     | 委譲先フロー  | 目的（何をするフローか） |
|--------------------------------------------|--------------------------|----------|---------------|--------------------------|
| コンテンツ訴求が目的のLP・PoCの画面モックのみ（UI・API・DB不要） | 静的サイト | 実装済み | new-static（Astro+Node.js固定） | Astroで、公開用の静的LP（ランディングページ）やPoCの画面モックを作る |
| API・DB・認証など動的機能（Node.js系）     | Webアプリ                 | 実装済み | new-project   | Node.jsで、APIやDBを持つ本格的なWebアプリケーションを作る |
| Tauri・Electron等 Web技術ベースのデスクトップアプリ | デスクトップアプリ | 実装済み | new-project（`recipes/tauri-init.md`等のscaffold手順を参照） | Web技術ベースのデスクトップアプリ（Tauri/Electron等）を作る |
| Flutter・React Native・Expo等スマホアプリ  | クロスプラットフォーム    | 実装済み | new-app       | Flutter等で、iOS/Android両対応のスマホアプリを作る |
| 画面UIが不要、ターミナル上で完結           | CLIツール                 | TODO     | （未実装）     | ターミナルで動くCLIツールを作る |
| Google Sheets・Workspace連携が中心         | Google Apps Script        | TODO     | （未実装）     | GAS等でGoogle Workspace連携ツールを作る |
| ネイティブSwift・Kotlin単体実装            | ネイティブアプリ          | TODO     | （未実装）     | ネイティブ実装（Swift/Kotlin）でアプリを作る |
| 特定言語・ランタイム自体の学習/サンプル環境構築（サイト・アプリの制作が目的ではない） | 言語・ランタイム環境 | TODO | （未実装。consultへ） | 特定の言語/ランタイムを動かせる環境を整え、学習・検証用のサンプルコードを作る |

NOTE: 「静的サイト」は純粋なLP・PoCの画面モック専用。ツールのサンプル集・ドキュメントサイト・
  言語環境の紹介など「実行環境が前提にある」依頼は、画面（HTML）が欲しいように見えても
  このカテゴリに含めない。判断に迷ったら、ステップ2の質問1（プロダクトか学習/検証用か）の
  回答を最優先の判断材料にする。「学習・検証のためのツール/サンプル/環境構築」と回答された
  場合、UIの要否に関わらず「静的サイト」「Webアプリ」より先に「言語・ランタイム環境」行を検討する。

ANALYZE: ヒアリング結果を対応表と照合し、最も適合するカテゴリを1つ選ぶ
  IF 複数の候補で判断がつかない:
    ASK USER: 判断に必要な点（例:「フロントエンドは必要ですか？」）を確認する
    WAIT_FOR: ユーザーの回答
  IF どの行にも明確に適合しない（近い行に無理やり当てはめている自覚がある）:
    # 例: 実行環境そのものが目的で、Webアプリでも静的サイトでもない依頼
    REPORT: "対応表のどのカテゴリにも明確には合いません。"
    ASK USER: どう進めますか？
      1. consultに相談する（調査ベースで進め方を考える）
      2. 一番近いカテゴリで妥協して進める
    WAIT_FOR: ユーザーの回答
    IF 1（consultに相談）:
      SUMMARY = ここまでのヒアリング内容（要望・制約・不一致の理由）
      READ {SKILL_DIR}/flows/consult/SKILL.md
      IF READ FAILED:
        REPORT: "フローファイルが見つかりません: {SKILL_DIR}/flows/consult/SKILL.md。SKILL_DIR の導出を確認してください。"
        STOP
      FOLLOW: そこに記述されたすべての手順を実行する。SUMMARY を前提として渡し、再ヒアリングしない。
      STOP
    ELSE:
      # 妥協して進める。以降の候補カテゴリはユーザーが選んだ近いカテゴリを指す

選定理由の一言 = 候補カテゴリと選定理由、そして対応表の「目的」列の文言を組み合わせたもの。
  **技術スタックへの言及（対応表の「委譲先フロー」列に注記があるもの。例: Astro+Node.js固定）と
  「目的」列の一文は必ずそのまま含める。** ユーザーの承認は「その委譲先フローが実際に何をするか」
  への承認でもあるため、目的やスタックを省略・言い換えて曖昧に承認を得ない。
  例: 「APIとDBが必要そうなので、Webアプリ（new-project / Node.js。APIやDBを持つ
  本格的なWebアプリケーションを作るフロー）が適しています」
  例: 「UIは必要だがAPI・DBは不要そうなので、静的サイト（new-static / Astro+Node.js固定。
  公開用の静的LP・PoCの画面モックを作るフロー）が適しています」

IF 選定カテゴリ.状態 == TODO:
  # 実装済みカテゴリと違い「このカテゴリでいいか」の承認と「TODOなのでどうするか」を
  # 別々に聞くと同じ内容を2回確認することになるため、1回にまとめて提示する
  PRESENT: "{選定理由の一言}が、対応レシピはまだありません（TODO）。"
  ASK USER: どう進めますか？
    1. consultに相談して、調査ベースで進め方を考える
    2. 対応表の別カテゴリで妥協して進める
    3. ここで終了する
  WAIT_FOR: ユーザーの回答

  IF 1（consultに相談）:
    SUMMARY = ここまでのヒアリング内容（要望・制約・選定カテゴリ名・TODOである理由）
    READ {SKILL_DIR}/flows/consult/SKILL.md
    IF READ FAILED:
      REPORT: "フローファイルが見つかりません: {SKILL_DIR}/flows/consult/SKILL.md。SKILL_DIR の導出を確認してください。"
      STOP
    FOLLOW: そこに記述されたすべての手順を実行する。SUMMARY を前提として渡し、再ヒアリングしない。
    STOP
  ELIF 2（妥協する）:
    ASK USER: 対応表から直接選んでもらう
    WAIT_FOR: ユーザーの選択
    SET 選定カテゴリ = ユーザーが選択したカテゴリ
  ELSE:
    STOP
ELSE:
  PRESENT: 選定理由の一言
  GATE: ユーザー承認
    IF 否定された:
      ASK USER: 対応表から直接選んでもらう
      WAIT_FOR: ユーザーの選択
      SET 選定カテゴリ = ユーザーが選択したカテゴリ
```

### ステップ 4: 委譲

```
# 選定カテゴリ.委譲先フロー は、ステップ3の対応表「委譲先フロー」列の値（例: new-static）を指す
READ {SKILL_DIR}/flows/<選定カテゴリ.委譲先フロー>/SKILL.md
IF READ FAILED:
  REPORT: "フローファイルが見つかりません。SKILL_DIR の導出を確認してください。"
  STOP
FOLLOW: そこに記述されたすべての手順を実行する

NOTE: ステップ2のヒアリングで判明済みの情報（フロントエンド要否・フレームワーク等）は、
      委譲先フロー内で同じ内容を再度質問しないこと。既知の回答として扱う。
```
