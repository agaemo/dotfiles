# TDD方針（build フロー用）

対象別のTDD必須/推奨判断と、バグ発見時の Bug-fix TDD 手順。
STACK != "static" のテスト戦略決定時、またはバグ発生時に読む。

## 対象別の方針

| 対象 | 方針 | 理由 |
|------|------|------|
| API ルート・ミドルウェア・認証ロジック | **TDD 必須** | DBバグ・認証バイパスの温床。後から追加しにくい |
| DBクエリ・マイグレーション | **TDD 必須** | スキーマ変更後に追加すると既存動作の担保が取れない |
| バリデーション・状態遷移関数 | **TDD 必須** | 境界値バグが本番で発覚しやすく、修正コストが高い |
| その他のビジネスロジック関数 | TDD 推奨 | ロジックの複雑度に応じて判断 |
| UI コンポーネント | 任意 | 実画面確認で代替可能 |
| サーバーレスエッジ関数 | ローカルエミュレーターで統合テスト | ユニットテストでは実行環境を再現できない |
| WebSocket・リアルタイムイベント | 統合テスト推奨 | イベントループの非同期性がユニットテストでは再現困難 |
| 外部API連携 | モックで単体テスト | 実APIへの依存を排除してFastを保つ |

TDD 必須の層を実装するときは `tester` エージェントを「TDDモード」で先に呼び出すこと。
`tester` が Red（失敗）を確認したら実装に進み、Green になったら次の層へ。

## Bug-fix TDD 手順

バグが見つかった場合は**フェーズを問わず**（UIコンポーネントのバグ・サードパーティライブラリ
起因が疑われるバグも含む）以下の手順で修正する。上表「UI コンポーネント: 任意」は
**実装時**の方針であり、バグ修正時には適用しない。

1. `tester` エージェントを「バグ修正TDDモード」で呼び出し、バグを再現するテストを書く
   （UIバグでも必ず1回は試みること。「サードパーティライブラリのバグでテストが書けなさそう」
   という予測だけで手順2以降をスキップしない）
2. テストが Red（失敗）になることを確認する（再現できない場合は再現手順を精査する）
3. バグを修正する
4. テストが Green になることを確認する
5. 補完モードで `tester` を再度呼び出してリグレッションテストを追加する

⚠️ PROHIBITED: テストを書かずに直接修正すること（同じバグが再発しても検出できなくなる）
⚠️ PROHIBITED: 推測に基づく修正とユーザーへの動作確認依頼を、テストを書かないまま複数回
  繰り返すこと。2回目の修正試行に入る前に、必ずこの手順に戻って再現テストを書くこと

### テスト環境の技術的制約でブロックされた場合

手順1の再現テストが、テスト環境固有の制約（例: 対象ライブラリがjsdom等のテスト環境で
正しく動作しない）で書けないと判明した場合のみ、以下に切り替えてよい:

1. 制約の内容を具体的にユーザーに報告する（「〜のため自動テストでは検証できません」）
2. ユーザーに手動確認を依頼する前に、まずコードレビュー的な精査（該当ライブラリの
   既知issue調査・実装の見直し）で最も確度の高い仮説を1つに絞ってから提示する
   （複数の仮説を順番に試してその都度ユーザーに確認を求めることを避ける）
