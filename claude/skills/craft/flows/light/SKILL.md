# light（軽量経路）

scope のヒアリング結果（SUMMARY）を前提にし、再ヒアリングしない。環境構築は、SKILL.md の「開発ランタイムの選定方針」に従う。

## 1. 対象の判定

業務ルール（時間・数量・権限・状態の変化）を持つ題材か。持たない（単純な変換など）なら、確認せず、手順3へ進む。

## 2. 確認（作り始める前に1回）

下表の観点のうち、依頼文に書かれていないもの（該当する観点は、最低1問ずつ）を、5問前後にまとめ、推奨案つきで、1つのメッセージで聞く。
「重複・競合」と「数量・容量」は、見落としやすいので、該当するなら必ず聞く。「おまかせ」と返されたときは、推奨案で進め、置いた前提は、完了報告に書く。
WAIT_FOR: ユーザーの回答（「おまかせ」でもよい）。回答を受けるまで、実装に進まない。

| 観点 | 確認する問いの例 |
|---|---|
| 時間 | 単位・刻みは。最短・最長の長さは。営業時間・利用できる期間・タイムゾーンは |
| 数量・容量 | 上限・下限は。定員・在庫は。1人（1アカウント）が同時に持てる数・1日あたりの上限は |
| 重複・競合 | 同時の操作・二重登録は。同じ利用者が、別の対象で、時間や期間が重なる登録をしてよいか |
| 期限・状態の変化 | キャンセル・変更の期限は。取消後の扱いは。有効期限（トークンなど）は |
| 権限・対象範囲 | 役割ごとの違いは。他人のデータへの操作は。管理者ができることの範囲は。自分の申請を自分で承認してよいか |
| 金額・単位 | 通貨・端数の丸めは。送料・割引・税・手数料の扱いは（金額・料金を扱うとき。注文の合計、請求、課金を含む） |
| 入力の制約 | 必須項目・形式・文字数・桁数は |
| 削除・保持 | 履歴の保持・削除の方式・個人情報の扱いは |

## 3. 構成

入口（HTTP のルート）・業務ロジック・データアクセスの3層に分け、依存は入口から内側へ向かう（データアクセスが業務ロジックを、業務ロジックが入口を、呼ばない）。
SQL はデータアクセス層だけに書く。1ファイルにまとめない（PoC・サンプルと明示された場合は、この限りでない）。ディレクトリ名は、その言語の流儀に合わせる（例: Go は `internal/{api,service,store}`、Node は `src/{routes,services,repositories}`）。

## 4. 実装

確認で決まったルールは、受け入れ条件として、テストに書く（先でも後でもよい）。完了報告に、各ルールの検証結果を1行ずつ書く。
