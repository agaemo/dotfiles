# investigate（調査フロー）

```
SKILL_DIR = このSKILL.mdが存在するディレクトリの2階層上の絶対パス
  # このファイルを /Users/alice/.claude/skills/craft/flows/investigate/SKILL.md で読んだ場合
  # → SKILL_DIR = /Users/alice/.claude/skills/craft
実行前提: カレントディレクトリは調査対象プロジェクトのルート（.craft/ はそこからの相対パス）
```

## 調査の種別

| 種別 | 内容 | 手順ファイル（種別が決まってから READ する） |
|---|---|---|
| A. 不具合・障害の原因 | 症状から原因を特定する | `flows/investigate/types/bug.md` |
| B. コード・仕様の理解 | 処理の流れ・影響範囲の把握 | `flows/investigate/types/understand.md` |
| C. 技術調査 | 実現可能性・選定材料の調査。自分のコードベースとの突き合わせまで行う | `flows/investigate/types/tech.md` |
| D. 性能・リソース | 遅い・重い原因の切り分け | `flows/investigate/types/perf.md` |

## ルール

PROHIBITED: ソースコード・設定の編集、コミット、外部サービスへの書き込み。
  例外はステップ4でユーザーが承認した issue 作成のみ。
PROHIBITED: ステップ4のユーザー承認なしに issue を作成すること。

IMPORTANT: **結論には必ず根拠と確度を付ける。** 確度は「確定（再現・直接証拠あり）」
「有力（状況証拠が揃っている）」「仮説（未検証）」のいずれか。根拠のない断定をしない。
原因が特定できない場合は「分からない」と報告し、不足している情報を示す。

IMPORTANT: **サブエージェントの扱い。**
- debugger / architect / researcher は subagent_type として登録されていない。
  Agent ツールで汎用サブエージェント（general-purpose 等）を起動し、各 `.md` の全文を
  プロンプトに貼り込んだ上で、対象プロジェクトの絶対パスと調査内容を末尾に追記する
- 非同期実行のため、完了通知が届くまで次の作業を進めない。ただし、互いに依存しない
  複数のサブエージェントは同時に起動してよい
- 結果が空・形式不正・原因未特定の場合は、その旨を報告に含め（確度は「仮説」以下）、
  自前の調査で補えるか試みる

- 再現用の一時ファイルは `.craft/` 配下に置く（例外は種別Aの手順に従う）
- データを変更しうる実行（アプリ起動・テスト・計測がローカルの DB・ファイルを変更しうる場合）は、
  実行前に次の手順でユーザーの許可を得る:
    PRESENT: 実行するコマンドと、変更されうるデータ
    GATE: ユーザーの許可
    WAIT_FOR: ユーザーの回答
    IF 許可されない: 実行せず、コード・ログの読解による調査に切り替える
- コマンド実行は、プロジェクトに `.mise.toml` があれば `mise exec -- <command>` 経由で行う
- 報告をファイルに保存している場合のみ、ステップ4の各分岐で報告の「状態」欄を更新する

## 手順

### ステップ 1: 受付と種別判定

```
IF consult から SUMMARY を渡されて起動された:
  SET 依頼の要約 = SUMMARY（同じ内容を再度質問しない）
ELSE:
  ASK USER: 調べたいこと（症状・対象・知りたいこと）を教えてください。
            エラーメッセージやログがあれば貼ってください。
  WAIT_FOR: ユーザーの回答
  SET 依頼の要約 = ユーザーの回答
ENDIF

ANALYZE: 依頼の要約から種別（A〜D）を判定する。複数にまたがる場合は主目的を優先し、
  残りは同じ調査の中で順に扱う。
IF どの種別にも判定できない:
  ASK: 種別（A〜D）の内容を示し、どれに近いかを確認する
  WAIT_FOR: ユーザーの回答
IF 調査に必要な情報（再現手順・発生条件・対象範囲）が不足している:
  ASK: 不足している点を1メッセージにまとめて質問する
  WAIT_FOR: ユーザーの回答
```

### ステップ 2: 調査

```
READ {SKILL_DIR}/<判定した種別の手順ファイル>   # 上記の表を参照
IF READ FAILED:
  REPORT: "手順ファイルが見つかりません: <パス>。SKILL_DIR の導出を確認してください。"
  STOP
FOLLOW: そこに記述された手順を実行する
  # 依頼の要約と判定した種別は、コンテキスト内の値をそのまま手順ファイルに引き継ぐ。
  # 複数種別にまたがる場合は、主目的の種別から順に実行する。
  # 互いに依存しないサブエージェントの起動（例: 種別Cの researcher と種別Aの debugger）は同時に行う
```

### ステップ 3: 報告

```
自己検証: 結論が根拠から論理的に導かれることを確認する。飛躍がある場合は、
  根拠を追記するか、確度を下げる

規模を判定する（根拠の数 = 報告の「根拠」欄に挙げる異なるファイルの数。再現結果・ログは1件につき1と数える）:
  小: 単一の種別で、根拠が3点以下
  大: 複数の種別にまたがる、または根拠が4点以上。後続の作業で参照されると明らかな場合も大
  迷う場合: チャットで報告し、ファイルに保存するか尋ねる

小 → チャットで報告する
大 → RUN: mkdir -p .craft/docs
     Write で .craft/docs/investigate-<題材を表す短い英語名>.md に保存する
     RUN: test -f <保存したパス> && echo OK で存在を確認する
     IF 保存に失敗した: 失敗したことを伝え、報告の全文をチャットで示す
     要点をチャットでも伝える
```

報告の形式:

```markdown
# 調査: {タイトル}

状態: 調査済み   <!-- 調査済み / 引き渡し済み（先） / 対応しない / 保留 -->
日付: {YYYY-MM-DD}
種別: {A〜D}

## 依頼・症状
## 結論（確度: 確定 / 有力 / 仮説）
## 根拠
- `file:行` — 何を確認したか
- 再現結果・ログ
## 検討して除外したこと
## 未確認事項
## 次の行動案
```

### ステップ 4: 引き渡し

```
PRESENT: 次の行動案を提示する（修正はここでは行わない）
GATE: ユーザーの判断
  選択肢:
    1. 調査のみで終わる（対応しない／保留）
    2. 対応方針が一つに決まり、修正の規模が小さい（局所的・追跡不要）
    3. 追跡が必要、または規模が大きい修正
    4. 対応方針が複数ありうる、または設計判断が要る
    5. もう少し調べる（追加で調べたい点を聞き、ステップ2に戻る）
    6. その他（自由記述。内容が1〜5のいずれかに該当すればそれに従い、該当しなければ内容に応じて対応する）
WAIT_FOR: ユーザーの選択

IF 1:
  ASK: 「対応しない」と「保留」のどちらにするか
  WAIT_FOR: ユーザーの回答
  状態を回答に応じて「対応しない」または「保留」に更新する
  REPORT: 「[craft] investigateフロー完了。以降は通常の会話として対応します」
  STOP
IF 2:
  状態を「引き渡し済み（直接修正）」に更新する
  REPORT: 「[craft] investigateフロー完了。以降は通常の会話として、調査結果をもとに修正します」
  STOP（以降はスキルの管理外で、調査結果を根拠に修正する）
IF 3:
  IF issue が未作成:
    PRESENT: 題名・本文（調査の要約。.craft/ は git 管理外のため、要点を本文に載せる）
    GATE: ユーザーの承認
    WAIT_FOR: ユーザーの承認
    RUN: gh issue create
    IF 失敗（認証エラー・リポジトリ不明等）:
      REPORT: 失敗の原因
      ASK: 「手動で作成する／直接修正に切り替える（選択肢2）／中止する」
      WAIT_FOR: ユーザーの選択
      IF 手動で作成する: ユーザーが issue 番号を伝えるまで待つ
      IF 直接修正に切り替える: 上記 IF 2 に従う
      IF 中止する: REPORT「[craft] investigateフロー完了。以降は通常の会話として対応します」→ STOP
  状態を「引き渡し済み（issue #番号）」に更新する
  REPORT: 「[craft] investigateフロー完了。以降は issue-triage で対応します」
  Skill ツールで issue-triage に issue 番号を渡して起動する
  IF 起動に失敗: issue 番号を示し、手動で `/issue-triage <番号>` を実行するよう案内する
  STOP
IF 4:
  状態を「引き渡し済み（consult）」に更新する（選択肢を提示する前に更新する）
  consult の選択肢整理に接続する:
    SET 引き渡し要約 = 調査結果の要約（結論・根拠・確度・検討した方針）
    SET 相談対象 = "既存システム"
    READ {SKILL_DIR}/flows/consult/SKILL.md
    IF READ FAILED:
      REPORT: "フローファイルが見つかりません: {SKILL_DIR}/flows/consult/SKILL.md。SKILL_DIR の導出を確認してください。"
      STOP
    FOLLOW: 「ステップ 3: 選択肢の整理・提案」から consult の最後（ステップ4の実行を含む）まで実行する（調査は完了済みのため
            ステップ1・2は実行しない。引き渡し要約を課題と調査結果として使う）。選択肢は調査結果の方針候補（例: 不具合の対処方針）を
            A / B / … として整理し、各項目（内容・メリット・デメリット・工数感）はテンプレートに
            合わせるが、テンプレートの見出し（移行・リファクタ・現状維持）には拘らない。
    # 以降は consult の手順（ユーザーの判断、ステップ4の実行）に従う。
    # ここでは STOP せず、終了は consult 側に任せる
IF 5:
  ASK: 追加で調べたい点
  WAIT_FOR: ユーザーの回答
  ステップ2に戻る（報告をファイルに保存済みの場合は、追加の調査結果を同じファイルに追記する）
```
