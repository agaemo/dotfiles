# new-runtime（言語・ランタイム環境セットアップ）

new-project が持つ重量な設計文書（要求定義書〜基本設計書）は不要なため、
ヒアリング→開発ランタイム確定→plan.md作成→build委譲という軽量な手順で完結させる。

## 手順

### ステップ 1: ヒアリング（メインClaude自身が実行）

```
SKILL_DIR = このSKILL.mdが存在するディレクトリの絶対パス
  # 例: /Users/alice/.claude/skills/craft/flows/new-runtime

REQUIRE: カレントディレクトリがプロジェクトルートであること

SELF: 以下を1つのメッセージで質問する
  # フロントエンドUI要否・DB/認証要否は scope フローのステップ2で既に確認済みのため
  # ここでは質問しない（scope/SKILL.md ステップ4のNOTE参照）。既知の回答として扱う
  # 質問1も、ここまでの会話で対象言語・ランタイムが既に明確に語られていれば省略し、
  # 既知の回答として扱う（再質問しない）
  1. 学習・検証したい言語・ランタイム・フレームワークは何か
  2. 環境構築の分離方法に希望はあるか
     （軽量なバージョン管理ツール=mise / コンテナによる完全分離=Docker等）
  3. ホスト環境を汚したくない等、他に制約はあるか

WAIT_FOR: ユーザーの回答

NOTE: ユーザーが会話の冒頭で提示した実装案・下書き（コマンド例等）は「叩き台」であり、
  正式な回答として扱わない。特に質問2（環境構築の分離方法）は後から変更すると手戻りが
  大きいため、下書きに書かれていても必ずここで明示的に確認する。
```

### ステップ 2: 開発ランタイムの確定

```
READ {SKILL_DIR}/../new-project/recipes/planner-checklist.md の「開発ランタイムの選定方針」
IF READ FAILED:
  NOTE: 読めない場合でも以下の原則に従うこと — 環境管理ツールはデフォルトを mise とし、
        未知の言語・ツールはまず mise registry で対応可否を確認してから個別インストールを
        検討する。ユーザーがDocker等の分離を希望した場合はそれに従う。

APPLY: 「開発ランタイムの選定方針」に従い、環境管理ツール・言語バージョン・
  セットアップコマンド・検証コマンドを確定する
  IMPORTANT: セットアップコマンド確定前に、SKILL.md冒頭の一般原則（未知のツール確認・
    scaffold実行前の管理ファイル退避・生成環境と実行環境のバージョン一致・
    scaffold自動依存の安定度確認）を必ず適用すること。

SET STACK識別子 = 対象言語の英小文字表記のみ（例: python・rust・go。既存の特別扱い値
  static・flutter・node と衝突しないよう注意する）
SET 環境管理ツール・言語バージョン・セットアップコマンド・検証コマンド = 上記で確定した値
  # 以降のステップ3・4で参照する変数として保持する
```

### ステップ 3: plan.md作成

```
ANALYZE: ヒアリング結果からレビュートラックを判定する
  - DBスキーマ変更・認証・決済・外部公開APIを含まない（通常の学習用・使い捨て） → A（既定）
  - いずれかを含む → B以上を提案し、ユーザーに確認してから確定する
SET レビュートラック = 上記で確定した値（A/B/Cのいずれか）

WRITE .craft/docs/plan.md:
  ## 相談内容
  [学習・検証したい対象、使い捨て/継続運用の別を1〜2文]

  ## レビュートラック: [レビュートラック]
  # A（軽量: verify → code-reviewer）/ B（標準: verify → qa → code-reviewer）/
  # C（フル: verify → security-reviewer → qa → code-reviewer → adversarial-reviewer）

  ## 開発ランタイム
  **STACK識別子:** [ステップ2で確定した値。build フロー再開時の自動判定に使われる]
  **環境管理ツール:** [ステップ2で確定した値]
  **セットアップコマンド:** ```[ステップ2で確定したコマンド列]```
  **検証コマンド:** [ステップ2で確定した値]

  ## 実行計画
  ### フェーズ1: 環境構築
  - 変更内容・変更ファイル・検証方法・ロールバックを記載

  ### フェーズ2: サンプルコードの動作確認
  - 学習対象の最小サンプルを実装し、動作確認する

  ## 開発コマンド
  # ステップ2で確定したセットアップ・検証コマンドから、実行・起動/ビルド/テストに
  # 相当するコマンドをそれぞれ埋める（該当しないターゲットは行ごと省略してよい）
  | ターゲット | 内容 | 実行コマンド |
  |---|---|---|
  | dev | 実行・起動 | [実際のコマンド] |
  | build | ビルド | [実際のコマンド] |
  | test | テスト実行 | [実際のコマンド] |

ASSERT EXISTS(.craft/docs/plan.md)
IF FAILED:
  REPORT: "plan.mdの書き込みに失敗しました。書き込み権限・ディスク容量を確認してください。"
  STOP
PRESENT: plan.mdの内容を要約して提示する
GATE: ユーザー承認
  IF 否定された: 該当箇所を修正して再提示する
  PROHIBITED: 承認を受け取る前にステップ4へ進むこと
```

### ステップ 4: build フローへ委譲

```
READ {SKILL_DIR}/../build/SKILL.md
IF READ FAILED:
  REPORT: "フローファイルが見つかりません: {SKILL_DIR}/../build/SKILL.md。SKILL_DIR の導出を確認してください。"
  STOP
FOLLOW: そこに記述されたすべての手順を実行する
  STACK = ステップ2で確定したSTACK識別子
  HAS_REVIEW_CHAIN = true（トラックはステップ3で確定しplan.md冒頭に宣言済みの値に従う）
  HAS_FRONTEND = scopeフローのヒアリング結果（フロントエンドUI要否）に基づく値
```

## 注意事項

- `intake` / `architect` / `designer` は不要（重量な設計工程を経ない軽量フローのため）
- 学習用サンプルであっても、DBスキーマ変更・認証・決済・外部公開APIを含むと判明した場合は
  レビュートラックをB以上に引き上げることをユーザーに提案する
