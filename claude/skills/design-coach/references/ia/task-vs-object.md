# タスク指向UIとオブジェクト指向UIの使い分け

確認状況: 対比の定義は出版社の目次と、書籍の第三者の解説に基づく。使い分けの判断軸は craft の designer.md（既存の判断基準）と一般的な経験則。

## 原則

| | タスク指向UI | オブジェクト指向UI |
|---|-------------|------------------|
| 操作の順序 | 動詞 → 名詞（やること → 対象） | 名詞 → 動詞（対象 → やること） |
| 画面の単位 | 手順（タスク）ごと | 対象の一覧・詳細 |
| 例 | 自販機（お金を入れる → 商品を選ぶ）、ATM（「振込」「入金」を先に選ぶ）、ウィザード | 生徒管理アプリ（生徒の一覧 → 生徒を選ぶ → 編集など）、ファイラー（ファイルを選ぶ → 操作を選ぶ） |
| 弱点 | モードが生まれる、タスクが増えるとボタンが増える | 手順が固定の一回限りの作業では回りくどい |

操作の順序は、CUI（コマンドを打って対象を指定。動詞が先）と GUI（対象を選び、メニューで操作。名詞が先）の違いにも対応する。

## なぜ生まれるか（タスク指向になる背景）

業務分析で「やること」を洗い出し、それが要件になり、そのまま画面構成になるため。順番どおりにやるだけのUIになりやすい。解説では、業務自体を対象中心に組み直すことが本質的な改善だと述べられている。

## 判断基準（経験則）

当てはまる項目が多い側を採る。拮抗する場合は混在にする。

OOUI 寄り:
- 対象が複数あり、関係が複雑
- 操作が状況で変わる（同じ対象に複数のアクション）
- 継続的に使うサービス
- デスクトップ・大画面が中心

タスク指向寄り:
- 手順が固定で、単機能
- 単発の手続き（申請、会員登録、決済）
- スマホ中心で、1画面1目的

## タスク指向が許容される場面

記事（Zenn）の整理に基づく。OOUI を基本としつつ、次のような場面ではタスク指向を意図的に残してよい。

- **対象が限定され、すでに選ばれているとみなせる**: ATM はカードを入れた時点で口座（対象）が決まっているため、操作（振込・入金）を先に選んでも不自然でない
- **検索から始まる**: 不動産サイトなど、対象（物件）を見る前に条件で探す流れが自然な場面
- **一括操作**: 「写真を選んで削除」は OOUI、「削除を先に選んで複数の写真を選ぶ」一括削除はタスク指向の形。後者は、大量の対象を一度に処理するときに有効

補足:
- 日常の行動は「対象 → 行為」の順で言葉にしやすい（犬を見て、なでる・餌をやる・散歩させる）。人が無意識に取る順序に沿うため、OOUI は使いやすいとされる
- 書籍は、タスク指向から OOUI への転換を、ほぼ機械的に行える汎用的な改善方法と位置づけている（記事による紹介）。一方で、記事の著者は、基本は OOUI を意識し、限定的な場面でタスク指向を組み合わせる、両方を同時に考えて使い分ける立場

## 混在の作り方

OOUI を軸に、登録など手順が決まっている部分だけウィザード型にする。

- 入口は対象の一覧または詳細から（「新規作成」「この申込を進める」など）
- 手順の途中でも、対象名や状態を見せ続ける
- 完了後は、対象の詳細に着地させる
- 手順が複数画面にわたっても、ブラウザの戻る・途中保存・中断からの復帰を考える

## エンジニア向け対応表

- モード: グローバルな可変状態に近い（いまの状態を知らないと操作が決まらない）
- 混在: ドメインモデルの中に、ワークフロー（Saga / プロセスマネージャ）がある構成に近い

## 失敗例

- 手順型の画面が、対象から切り離されている（「何についての手続きか」が途中で分からなくなる）
- 全部をOOUIにして、単発の申請まで一覧と詳細を経由させる
- 全部をウィザードにして、継続利用者が毎回手順をたどらされる

## チェックリスト

- [ ] 画面ごとに「対象中心」か「手順中心」かを言語化したか
- [ ] 手順中心の画面は、入口と出口が対象につながっているか
- [ ] 継続利用者向けに、近道（対象から直接操作）があるか
- [ ] タスク指向を残す箇所（一括操作、検索起点、対象が固定の場面）は、意図して残したものか
