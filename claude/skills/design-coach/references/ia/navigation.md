# ナビゲーション設計

確認状況: NN/g の3記事（メニュー設計チェックリスト、縦ナビ、現在地の提示）を取得して内容を確認済み。数値は記事に記載があるものだけを出典付きで記し、他は経験則と明記。

## 原則

ナビゲーションは「どこにいるか」「何があるか」「どう動くか」の3つに答える。

## 適用ルール

### 1. 見えるようにする
- 大画面ではナビを隠さない。ハンバーガーは小画面向け（NN/g）
- 置く場所は、利用者が予想する位置。Web サイトはヘッダー、アプリは画面左側、ローカルナビは左側（NN/g）
- 文字は背景と十分なコントラストを取る
- 大画面で、開いたメニューが画面全体を覆わない（別ページに移動したと誤解される）

### 2. 現在地を示す（最も多い失敗とされる）
複数の手がかりを組み合わせる。1つだけに頼らない。
- ナビの選択中項目を目立たせる（色を変える、位置をずらす。両方併用が望ましい）
- 見出し（左揃え、階層が分かる形）
- 一意で説明的なページタイトル
- 人が読める URL
- パンくずリスト（深い階層では必須。ナビの変化だけでは足りなくなる）
- ステップ表示（番号と名称。申込フォームなど）
- 日付などの文脈の手がかり
- エラーページや検索結果0件でも、現在地の手がかりと次の行動（候補リンク、全体ナビ）を出す。行き止まりを作らない

### 3. 選択肢を伝える
- ラベルは、分かりやすく、具体的で、馴染みのある語。造語・専門用語・抽象的な分類を避ける
- ラベルは素早く走査できるように。縦メニューは左揃え、重要な語を先頭に置く
- ラベル用語は、ナビ全体で統一する
- 項目が多い場合に、アイコンを補助として使ってよいが、**テキストラベルは残す**（日常的に使い込むアプリを除き、アイコンのみは避ける）

### 4. 操作しやすくする
- リンクは押しやすい大きさにして、間隔を空ける（NN/g 記事は具体的なピクセル値を示していない）
- サブメニューがあることは、矢印などで示す
- サブメニューは、ホバーではなくクリックで開く（タッチ・キーボード利用者のため）
- ドロップダウンは1階層が基本。2階層は使いにくく、3階層以上は非推奨。階層が深い場合は、メガメニュー（2〜3階層程度）か案内ページを使う
- 長いページでは、ナビを固定表示する（特に小画面）
- よく使う項目は、メニューを開く操作の近くに置く（フィッツの法則）
- 奇抜なナビを避け、馴染みのある形を選ぶ

## 左サイドバー（縦ナビ）— 業務系の標準形

利点（NN/g）:
- 多数のトップレベル項目を収められる
- 項目の追加がしやすく、再設計が不要
- 走査しやすい。ユーザーは画面左側に注目し、**画面の左半分を見る時間が約80%**とされる（NN/g の記載）
- Slack や Gmail など、デスクトップ系Webアプリで馴染みがある
- モバイルへの展開時に、書体・罫線・順序を共通化しやすい

使う場面:
- 項目が多い、成長中、具体的なカテゴリを前面に出したいサービス
- 横ナビに収まらない場合

トレードオフ:
- 横ナビよりコンテンツ領域が狭くなる（NN/g の事例では、コンテンツ対クロムの比が縦ナビで約5:1、横ナビで約12:1）
- 小型ディスプレイ・タブレットでは、ブレークポイントごとに縦ナビを使うか決める

設計:
- 背景色・文字色・罫線などで、他と区別して目立たせる
- 同じカテゴリを、横ナビと縦ナビの両方に置かない
- テキストラベルを常時表示する
- 項目が長くなる場合、重要度の低いものを下に置く（下ほど見えにくい）
- ラベルは左揃え、キーワードを先頭に
- 幅（px）や折りたたみの閾値は、NN/g の記事に記載なし。プロダクトごとに決める（経験則では 200〜280px 程度が多い）

## OOUI との関係

- ルートナビゲーションの項目は、**メインオブジェクト**（`references/ia/ooui.md`）にする。タスク名（「申請する」「承認する」）を並べない
- 各項目の遷移先は、そのオブジェクトの**コレクションビュー（一覧）**にする
- 一覧から、行を選んで詳細（シングルビュー）へ。詳細内に、関連オブジェクトへのリンクと、アクションを置く

## 失敗例

- 現在地がどこにも示されていない
- ナビがタスクの羅列になり、対象が見えない
- アイコンだけのナビで意味が分からない
- ホバーでしか開かない多段メニュー
- 同じ項目が横と縦に重複している
