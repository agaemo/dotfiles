# OOUI（オブジェクト指向UI）

確認状況: 概要・目次は出版社ページで確認済み。原則4つは書籍の第三者の解説で一致（書籍本文は私は未参照）。設計プロセスの5段階は、書籍を読んだユーザーからの情報で、目次の3ステップと一致。ステップ1の細かい手順は第三者の解説1件のみに依存。ステップ3は未確認。

## 原則

UI を「ユーザーが扱うもの（名詞=オブジェクト）」から組み立てる。ユーザーはまず対象を見て選び、その後に操作（アクション）を選ぶ。

- 操作の順序は **オブジェクト選択 → アクション選択**（名詞 → 動詞）
- オブジェクトは知覚でき、直接働きかけられる
- オブジェクトは自身の性質と状態を画面で表す
- 複数のオブジェクトが協調して、1つのUIを構成する

対比: タスク指向UIは「やること（動詞）」から始め、対象を後から指定する（使い分けは `ia/task-vs-object.md`）。

例: 生徒管理アプリは、生徒の一覧 → 生徒を選ぶ → 編集などの操作、の順。宅配ピザで、商品を選ぶ前にログインや「今すぐ配達」を求める構成は、動詞が先で、どこを押せば注文できるか分かりにくい（記事の指摘）。

効果: 手順を覚えなくてよい（NN/g の「再認優先」と同方向）、画面が対象ごとの「一覧」「詳細」に集約される、機能追加が「対象にアクションを足す」で済む、モード（途中で抜け出す必要のある状態）が生まれにくい。

## ドメインモデリングとの対応

**私の類推であり、書籍の定義ではない。**

| OOUI | ドメイン設計 |
|------|------------|
| オブジェクト | エンティティ |
| メインオブジェクト | 集約ルートに近い（画面の主役） |
| 多重性 | カーディナリティ |
| 付随オブジェクト → プロパティ | 属性 / 値オブジェクト |
| アクション | メソッド / ユースケース |
| コレクションビュー / シングルビュー | 一覧（index）/ 詳細（show） |
| ルートナビゲーション | トップレベルのリソース |

解説には「UML やドメインモデリングの経験があればオブジェクトの抽出は容易」とある。デザイナーには「エンティティ」の理解が壁になりやすい、とも。

## 設計プロセス

書籍を読んだユーザーからの情報による流れ（括弧内は出版社の目次の3ステップ）:

1. 実現したいことを、思いつくまま書き出す（Miro、付箋など。タスクから始めてよい）【ステップ1】
2. 書き出した内容から**名詞**をピックアップする【ステップ1】
3. 名詞から**モデル**を検討する。**同じ名詞でも文脈で指すものが違う場合があるので注意**【ステップ1】
4. モデルから**インタラクションと View** を考える【ステップ2: ビューとナビゲーション】
5. View から**画面**を検討する【ステップ3: レイアウトパターンの適用】

要点:
- タスクは捨てず、名詞を取り出す材料にする。**UI の構成そのものにしない**
- 同名異義: 同じ「顧客」「注文」でも部署や場面で意味や属性が違う。無理に1つにまとめない（ユビキタス言語と境界づけられたコンテキストの問題に近い。私の類推）
- 画面（レイアウト）を先に描かない。モデルとビューが先

### ステップ1の細目（第三者の解説）

1. 名詞と、名詞同士の関係を洗い出す
2. 名詞を汎化して粒度を揃える（「A社の顧客」「B社の顧客」→「顧客」）
3. 関係をつなぎ、オブジェクトを特定する
4. **メインオブジェクト**を決め、多重性を決める
5. 付随するオブジェクトは**プロパティ**にする
6. タスクから**アクション**を見つけ、対象に紐づける

クラス定義と同じ作業で、業務の深い理解が要る。粒度が揃わないと後のビューがぶれる。

### ステップ2の細目（第三者の解説）

- **コレクションビュー**: 同種を複数並べる（眺める・探す・選ぶ）
- **シングルビュー**: 1つを表示する（よく見る・操作する）
- **ルートナビゲーション**: メインオブジェクトから選び、トップレベルのナビに置く
- 早い段階でメインオブジェクトの一覧を見せ、「選んで操作する」流れを推測させる

### ステップ3

経験則としての良いパターンを画面配置に当てはめる。デスクトップとモバイルで検討が変わる。詳細は書籍で要確認。配置の一般論は `spacing-layout.md` と `patterns/` を参照。

## 相談で答えるときの型（画面構成）

1. 名詞の抽出と、同名異義の注意（要件のタスクは捨てない）
2. メインオブジェクト（3〜7個）と、付随（プロパティ）
3. ルートナビゲーション（オブジェクト中心。タスク名を並べない）
4. ビュー表（オブジェクト × 一覧 / 詳細）。ステータス別の画面は作らず、状態フィルタに
5. 手順型の扱い（併用の判断と理由。入口・途中・完了後は対象から離れない）
6. 画面一覧（初版）。未検証の点（ステップ3）を明記。前提確認では、利用者の役割と権限を聞く

## 適用ルール

- 画面構成は「対象の一覧」「対象の詳細」を軸にする。操作は、詳細や一覧の行に置く
- ボタンをタスクの数だけ並べない。対象を選んだ後に、そのとき意味のあるアクションを出す
- 業務分析の「やること一覧」をそのまま画面構成にしない
- 状態（ステータス）は独立したオブジェクトにせず、**対象の状態として表示**する（バッジ、色、ラベル）
- OOUI は万能ではなく、**併用・使い分けが前提**（解説の筆者は万能性に疑問を持つ）。手順型の画面の扱いは `ia/task-vs-object.md`

## 失敗例

- 要件のタスク一覧が、そのままメニューになる（対象が見えない）
- 対象を選ぶ前に操作を選ばせる（モードが生まれる）
- 名詞の粒度がばらばらで、一覧が何の一覧か曖昧
- ステータスごとに画面を分ける。1つの一覧に状態フィルタを付ける方が拡張しやすい（経験則）

## チェックリスト

- [ ] 書き出しから名詞を取り出し、タスクをそのまま画面にしていない
- [ ] 同じ名詞が文脈で別物を指していないか確認した
- [ ] メインオブジェクトを3〜7個程度に絞った
- [ ] 各オブジェクトに一覧と詳細がある
- [ ] トップレベルのナビがメインオブジェクト中心
- [ ] 操作は、対象を選んでから出ている
- [ ] 状態は対象の属性として表示している
