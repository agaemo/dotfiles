# ARIA とネイティブ HTML

確認状況: W3C「Using ARIA」と WCAG 2.2 の 4.1.2 を取得して確認済み。

## 原則

**ネイティブ HTML で足りるなら、ARIA を使わない。** ARIA は意味を補う道具で、動作（フォーカス、キー操作）は別に実装が要る。

## ARIA の基本ルール（W3C）

1. **ネイティブ HTML を優先**: 必要な意味と動作を持つ要素があれば、それを使う。ARIA で別の要素を流用しない。例外: HTML に機能がない、実装・サポートが不十分、デザイン上ネイティブ要素のスタイルを変えられない場合
2. **ネイティブの意味を変えない**: やむを得ない場合を除く。見出し `h2` に `role=tab` を付けるのでなく、`div role=tab` の中に `h2` を入れる
3. **対話的な ARIA 部品はキーボードで操作できる**: フォーカスを受け、標準的なキー操作に反応する。`role=button` は Enter（Mac では Return）と Space の両方で実行できるようにする
4. **フォーカス可能な要素に `role=presentation` や `aria-hidden=true` を使わない**: 何もない所にフォーカスが当たる。親に `aria-hidden=true` を付けると、中の操作要素も隠れる。`display:none` や `visibility:hidden` の要素は、もともとフォーカス不可・アクセシビリティツリー外なので、追加不要

## 4.1.2 名前・役割・値（WCAG A）

すべての UI 部品で、名前と役割がプログラムから判別でき、状態・値を設定でき、変化が支援技術に通知される。

実務の順:
1. **標準 HTML 要素**（`button`、`input`、`select`、`a`）を使う。仕様どおりに使えば基準を満たす
2. ラベルは **`label` 要素**で関連付ける。見えるラベルを置けない場合に限り `aria-label` などを検討
3. 既存の要素をスクリプトで独自部品にする場合は、**名前・役割・状態・変化の通知**をすべて自前で担保し、ARIA を併用する
4. ゼロから独自部品を作る場合は、ARIA とイベント処理で、役割・状態・名前を完全に実装する

よくある失敗: `div`/`span` をボタン化したが `role` がない、UI 部品に判別可能な名前がない、フォーカスの変化が通知されない、リンクを疑似的に作って正しく動かない。

## 設計・実装への示唆

- デザインシステムのコンポーネント（モーダル、タブ、メニュー、コンボボックスなど）を自作する場合は、**キー操作と ARIA の仕様（W3C の ARIA Authoring Practices の該当パターン）**を先に確認する（未取得。要確認）
- 無効状態: NN/g は、フォーカスは受けつつ非活性を伝えるため `aria-disabled="true"` を勧める（検索結果の要約。本文未取得。`patterns/permissions-audit.md`）
- 装飾イラストは空の `alt`（`alt=""`）で、支援技術にスキップさせる（Carbon の空状態パターン）

## よくある落とし穴（経験則。スクリーンリーダーでの実機確認は未実施）

- 見出しを文字ごとに分割して演出する場合は、見出しに `aria-label` で全文を付け、分割した文字を `aria-hidden` にする。**見出しの中に補足文など別の内容を入れない**（`aria-label` が名前を上書きし、読まれ方が実装依存になる）
- `aria-live` は、頻繁に変わる文言（スクロール連動で入れ替わるキャプションなど）に付けると、読み上げが多くなる。必要なときだけ付ける
- 装飾の Canvas や SVG は `aria-hidden="true"`。情報を持つなら、同じ内容を本文のテキストにも置く
- 固定高さと `overflow:hidden` の入れ物は、利用者が行間・字間を広げると内容が切れる（WCAG 1.4.12。`a11y/wcag.md`）

## エンジニア向け補足

標準要素は「型付きで検証済みの部品」、独自の `div` 部品は「型のない any で、契約（名前・役割・状態）を全部自分で実装する」状態に近い。
