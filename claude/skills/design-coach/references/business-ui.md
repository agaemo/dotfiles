# 業務系UI（管理画面・フォーム・テーブル）

**このファイルは未検証の概要。** フォーム・テーブル・検索・ウィザード・エラー・空状態は、出典つきの詳細を `references/patterns/` に分離した。両者が食い違う場合は `patterns/` を優先する。

目的は「正確に・速く・迷わず」処理させること。装飾より**一貫性・密度・状態の明示**が品質を決める。

## 基本方針

- **一貫性が最優先**: 同じ操作は同じ見た目・同じ位置・同じ文言。例外を作るたびに学習コストが増える
- 情報密度は高くてよいが、**グルーピングと階層は必須**。詰めるなら余白で分け、境界線を乱用しない
- 文字サイズ・行間: デジタル庁DSは、本文とUIを **16px 以上**を基準とし、14px は基本使わない。情報量優先の業務画面は行高 120%、管理画面は 130%（Dense スタイル、14〜17px）と定義している（`ja/typesetting.md`）。数字は `tabular-nums`（経験則）
- 色は**意味に使う**（状態・警告・選択）。装飾の色は最小限
- 主要操作は画面あたり1つを強調（塗りつぶしボタン）。他はアウトライン/テキスト

## 画面の型

- **一覧（リスト/テーブル）**: 検索・絞り込み・並べ替え・ページング・一括操作。上に操作、下にデータ
- **詳細**: 見出し(対象名+状態) → 主要な属性 → 関連情報 → 操作
- **フォーム/入力**: 1カラムが基本。関連項目をグルーピングし、見出しで区切る
- **ダッシュボード**: 重要指標を上、詳細を下。チャートは `dataviz` スキルの方針に従う

対象(名詞)中心の構成（OOUI）かタスク(動詞)中心の構成かは、craft の designer（フェーズ1）の判断基準を参照する。

## フォーム

- ラベルは**入力欄の上**（縦並び）。左置きは幅が広い画面でのみ。プレースホルダーをラベル代わりにしない（入力すると消える）
- 必須/任意を明示する。任意項目を減らし、任意に「（任意）」と付ける方針が出典（NN/g、GOV.UK）にある。必須へのアスタリスクは GOV.UK が非推奨。全体で統一する
- 入力例・書式のヒントは、欄の下に小さく
- エラーは**欄の近くに、原因と対処を文章で**（「正しく入力してください」ではなく「半角数字で8桁入力してください」）
- バリデーションのタイミング: 既定は**送信時**。最初の blur で即エラーにしない（GOV.UK、NN/g）。ミスが起きやすい欄だけインライン検証を足す。詳細は `patterns/forms.md`
- 送信ボタンは主要色、キャンセルは弱い見た目。破壊的操作（削除）は赤+確認
- 長いフォームは、**セクション分割**・進捗表示・自動保存を検討する
- フォーカスリングは必ず見えるようにする（キーボード操作・アクセシビリティ）

## テーブル

- 数値は**右揃え**、文字は左揃え、見出しは対応する列と同じ揃え
- 行の高さ: 密 / 標準 / ゆったりの3段階を用意し、ユーザーが切り替えられるとなお良い（具体値は経験則。Carbon の例は 32 / 40 / 48px。`patterns/tables.md`）
- 行ストライプ or 薄い罫線のどちらか（併用しない）
- ヘッダーは固定(sticky)、ソート可能な列は矢印アイコンで示す
- 空のとき: 「データがありません」だけでなく、**次の行動**（作成ボタン、絞り込み解除）を出す
- 長いテキストは省略(…)+ツールチップ。折り返しで行の高さが揃わなくなるのを避ける
- 操作列は右端。行内の操作が多いときは「…」メニューにまとめる

## 状態の設計（全部作る）

| 状態 | 設計 |
|------|------|
| 通常 | 基準 |
| hover | 背景/色を少し変える |
| focus | 明確なリング（2px、コントラスト3:1以上） |
| active | 押し込み感（少し暗く） |
| 無効 | 薄くする+カーソル変更。なぜ無効かをツールチップで示せるとなお良い |
| ローディング | スケルトン or スピナー。ボタンは二重送信防止 |
| エラー | 赤+アイコン+文章 |
| 空 | 説明+次の行動 |
| 成功 | トースト/インライン。自動で消す場合は数秒、エラーは自動で消さない |

## ナビゲーション

- サイドバー: 項目が多い/階層がある管理画面。現在地をハイライト、グループに見出し
- トップバー: 項目が少ない、またはグローバルな操作（検索、ユーザー）
- パンくず: 階層が深いとき。現在地と戻り先
- 項目の並びは**使用頻度順または業務フロー順**。アルファベット順は避ける

## 文言

- ボタンは動詞（「保存」「追加」「削除」）。「OK」「はい」は避ける
- 確認ダイアログは、**何が起こるか**を書き、ボタンも具体的に（「削除する」「キャンセル」）
- 専門用語は利用者の語彙に合わせる。内部用語を画面に出さない

## 業務系らしさから抜けるための手がかり

- 色: ニュートラルを純グレーにせず、ブランド色に寄せる。アクセントを1色決めて役割に一貫して使う
- タイポ: システムフォントのまま使わず、Noto Sans JP など1つを選び、ウェイトで階層を付ける
- 余白: スケールを決め、グループ間を内側の2倍にする
- 角丸/影: 値を2〜3段階に固定し、全体で使い回す
- 細部: アイコンのサイズ・線の太さを統一する（ライブラリを1つに絞る）

## よくある失敗

- 同じ意味のボタンが画面ごとに色や位置が違う
- 全ての項目が同じ重みで並び、重要な情報が埋もれる
- エラーメッセージが抽象的
- 空状態が空白のまま
- テーブルの数字が左揃えで桁が読めない
