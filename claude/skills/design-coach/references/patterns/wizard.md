# ウィザード（段階入力）

確認状況: NN/g「Wizards: Definition and Design Recommendations」（2017）を取得して確認済み。ステップ数の上限は記事に記載なし。

## 原則

入力を、決まった順序のステップに分けて進める仕組み。利用者には一本道に見えるが、裏では前の入力に応じた分岐がある。

## 使うべき場面・向かない場面

使う:
- 初心者や、その分野の知識が少ない利用者
- 設定やセットアップなど、**めったに行わない**処理

向かない:
- 頻繁に繰り返す作業（クリック数が増え、操作コストが高い）。繰り返す人には、速い別経路を用意する
- 利用者が自由に順番を選べる必要がある作業（ウィザードは順序固定が前提）

利点:
- 1画面の項目が減り、圧倒されにくい。認知負荷が下がり、入力ミスも減る
- 1画面に余裕が出て、説明を近くに置ける
- 分岐を設計すれば、利用者は自分に関係するステップだけ見る

欠点:
- 繰り返しの操作コスト
- ステップをまたぐ比較や、情報の移し替えが難しい
- 途中離脱で入力が失われやすい（フォームにも共通）
- 利用者の自由度を制限する

## 適用ルール

1. **全体像を示す**: 全ステップを一覧か図で見せ、現在地を強調する。各ステップは短く分かりやすいラベルに。全体の長さを事前に伝える（ステップ数の上限は記事に記載なし）
2. **進捗を示す**: 現在のステップを明確にし、完了と未完了を区別する
3. **順序を固定する**: 前のステップが終わらないと次に進めない
4. **ボタンの名称**: 「次へ」「戻る」のような汎用ラベルは情報が乏しい。**次に何をするかが分かる名称**にする。戻る操作は**明示的なボタン**で用意する（タブ操作だけにしない）
5. **途中保存と再開**: 中断しても保存でき、後で再開できる。保存ボタンは注目が集まる位置に
6. **ステップを自己完結させる**: 他の画面や前のステップの情報を前提にしない。必要な情報は、そのステップ内で確認できるように
7. **ヘルプは入力欄を隠さず、隣に**表示する
8. **前回の入力を初期値**にする（次回の便利さ）

## OOUI との関係

- 手順型の画面は、**入口を対象の一覧・詳細から**にし、途中でも対象名・状態を見せ、完了後に対象の詳細へ戻す（`ia/task-vs-object.md`）
- モーダルのウィザードは、背景にある操作に必要な情報を隠すことがある（NN/g）。必要な情報が背景にある場合は、画面遷移型にする

## 失敗例

- 毎日使う作業が、毎回ウィザードで5ステップかかる
- 途中で閉じると、入力が全部消える
- ステップ名が「ステップ1」「ステップ2」で、内容が分からない
- 「次へ」「戻る」だけで、次に何が起きるか分からない
- 前のステップの内容を、次のステップで確認できない

## チェックリスト

- [ ] この作業は低頻度か、初心者向けか（高頻度なら別経路がある）
- [ ] 全体像・現在地・完了状況が見える
- [ ] 戻るボタンが明示されている
- [ ] 途中保存と再開ができる
- [ ] 完了後の着地先が、対象の詳細になっている
