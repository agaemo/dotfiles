# フォーム設計

確認状況: NN/g の「Web Form Design」と「Error-Message Guidelines」、GOV.UK Design System の「Validation」「Question pages」を取得して内容を確認済み。デジタル庁 DS-670.1 は該当節を確認。**検証タイミングの結論は複数出典の私の統合**（下記）。

## 原則

フォームは「聞く量を減らし、迷いなく書けて、間違えても直しやすい」状態が目標。

根拠（NN/g の紹介）: CHI 2014 の研究で、ガイドラインに沿ったフォームは初回でエラーなく送信できた割合が **78%**、沿っていないフォームは **42%** で、完了時間も短かった。

## 適用ルール

### 項目と構成
- **項目を減らす**: 他から導出できる、後で聞ける、省略できる情報は削る（NN/g の事例では 6項目 → 2項目）
- **1カラム**にする。1行に1項目。市・都道府県・郵便番号のように短く関連が強い項目だけ同じ行に置いてよい
- **論理的な順序**にし、Tab キーの移動順も確認する。選択肢は利用頻度が高いものを先頭に
- 関連項目はグループ化し、見出しで区切る（グループタグと label 属性も設定する）
- 任意項目は**1〜2個に抑え、「任意」と明記**する。GOV.UK は、必須にアスタリスクを付けず、任意項目に「(optional)」を付ける方針
- 有効な回答として成立するなら「わからない」を選べるようにする（GOV.UK）

### ラベルとヒント
- ラベルは入力欄の近くに。モバイルや短いフォームは**欄の上**、長いデスクトップフォームは**横**もあり（NN/g）。複数の欄から等距離になる配置は避ける
- **プレースホルダーをラベル代わりにしない**（NN/g は避けるよう勧める）
- 入力条件・書式（パスワード要件、電話番号の書式）は、**入力前に**具体的に示す。エラーで初めて分かる仕様にしない
- ヒントは短い1文に。長い説明やリンクをヒントに入れない（GOV.UK。スクリーンリーダーが全文を読み上げるため）

### 入力欄
- 種類は入力内容に合わせる。**選択肢が2〜3個ならドロップダウンでなくラジオボタン**（NN/g）
- 幅は想定入力に近づける（NN/g の調査では、居住都市名の99.9%が19文字以内。日本語の氏名・住所は別途確認が必要）
- 複数の書式で書かれても意味が変わらないもの（郵便番号、電話番号のハイフン）は、**いずれも受け付けて正規化**する（GOV.UK）
- **リセット・クリアボタンは置かない**（誤って入力が消えるリスクが大きい。NN/g）。取り消しが必要ならキャンセルを用意し、送信ボタンより目立たせない
- レンジスライダーは、ドラッグが難しい人がいるため避ける。使うならドラッグ以外の回答方法も用意（GOV.UK）

### 検証（バリデーション）とエラー
- **サーバー側の検証は必須**。クライアント側は、必要が確認できた場合に追加する。両方ある場合はルールを矛盾させない（GOV.UK）
- **検証のタイミング**:
  - GOV.UK: 欄を離れた時点では検証せず、**「続ける」「送信」を押したときに検証**する。入力途中の検証は、調査で利益が確認された場合のみ
  - NN/g: **空欄のままフォーカスが外れた程度を、エラーとみなさない**。ミスが起きやすい入力にはリアルタイムのインライン検証を検討する
  - 統合（私の推奨）: **既定は送信時に検証**。パスワード要件や文字数制限など、入力中に分かった方が手戻りが減る欄に限って、入力後（または入力中）のインライン表示を足す。最初の blur で即エラーを出さない
- エラーの表示:
  - 該当欄の近くに表示し、ページ上部にエラーの一覧（サマリー）も出す。キーボードフォーカスをサマリーへ移す（GOV.UK）
  - ページ `<title>` の先頭に「Error:」を付ける（GOV.UK。スクリーンリーダーが早く読み上げる）
  - 色だけに頼らず、枠線・アイコン・太字なども併用する（NN/g。色覚多様性のある人は世界で約3億5千万人とされる）
  - **入力済みの値は消さずに保持**する（NN/g、GOV.UK）
  - ブラウザ標準のエラー表示（HTML5 検証）は使わず、`novalidate` で無効にして統一する。`required` 属性も使わない（GOV.UK の方針。独自実装でアクセシブルに作る前提）
- WCAG の対応: 3.3.1（A: 誤りの項目を特定し、テキストで説明）、3.3.2（A: すべての入力欄にラベルか指示）、3.3.7（A: 同じプロセスで同じ情報を再入力させない）。詳細は `a11y/wcag.md`
- 文言の書き方は `references/patterns/errors-undo.md` を参照

### 構造に関わる判断
- GOV.UK は**原則1ページ1質問**（公共サービス向け。理解しやすく集中できる）。ただし、**繰り返し作業が多い社内サービスなど、調査で裏付けがあれば複数質問をまとめてよい**とも明記している
- 同じ情報は2度聞かない。既存の回答を事前入力する
- 戻るリンクをページ上部に置き、ブラウザの戻るが期待どおり動くようにする（GOV.UK）
- ボタンの文言は汎用的な「次へ」より、**次に起こることが分かる語**に（NN/g のウィザード記事も同方針）

## 使い分け

| 状況 | 方針 |
|------|------|
| 公共サービス、初見の利用者が多い | 1ページ1質問に近づける（GOV.UK） |
| 継続利用する業務システム、入力が多い | 1画面にまとめ、グループ化と見出しで整理（調査で確認） |
| めったに行わない複雑な手続き | ウィザード（`patterns/wizard.md`） |
| 頻繁に行う入力 | 1画面、キーボードで完結、近道を用意 |

## 失敗例

- 6項目で足りるのに、15項目を並べて離脱される
- プレースホルダーだけで説明し、入力すると何の欄か分からなくなる
- エラーで入力内容が消える
- 最初の blur で赤いエラーが出て、利用者に責められている印象を与える
- 色だけでエラーを示す
- 「入力値が不正です」のように、何をどう直すか分からない
