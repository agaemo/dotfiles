# エラー設計・確認・取り消し（Undo）

確認状況: NN/g「Error-Message Guidelines」「Confirmation Dialogs Can Prevent User Errors — If Not Overused」を取得して確認済み。デジタル庁 DS-670.1 の4.2節（使用エラー対策）の本文を確認済み。

## 原則

エラー対策は3段構え。**未然に防ぐ → 防げなければ確認する → 起きたら元に戻せる**。この順で考える。確認ダイアログは最後の手段で、**多用すると読まれなくなる**。

## 1. 未然に防ぐ（フェイルセーフとフールプルーフ）

デジタル庁 DS-670.1（4.2）の整理:
- **フェイルセーフ**: 使用エラーが起きても、**安全側に収束するよう**にする
- **フールプルーフ**: 使用エラーが起きても、**問題を引き起こす機能が働かないよう**にする
- 検討すべき場面として、間違った操作、必要な操作の漏れ、手順の省略、正規の順序からの逸脱、余計な操作、技能や知識が不十分な操作者、状況の誤認、完了条件が複数あって片方のやり忘れを誘発するとき、が挙げられている
- 特定すべき重大な脅威の例: 個人情報の漏えい、**誤った申請・手続**、**情報の誤削除・誤登録**、**権限のない利用者による機能変更**、利用者の財産の損害

具体策（NN/g と一般的な設計）:
- 起こりやすい誤りを検知して警告する（例: 添付忘れの確認）（NN/g）
- 入力の制約を UI で表現する（選択肢の限定、型に合った入力欄、範囲の制限）
- 危険な操作のボタンを、通常操作から離す・目立たせない（経験則）
- 期限切れ・競合（他の人が先に更新した）を検知して、上書きしない（経験則）

## 2. 確認ダイアログ（実行前）

NN/g の要点:
- **重大な結果を伴う操作、取り消せない操作**にだけ使う。ルーティン操作には使わない
- 多用すると、利用者は読まずに承諾する。確認が防止機能を失い、本当に重要な警告まで見落とされる
- **文言は具体的に**: 「本当に実行しますか?」のような汎用文でなく、何が・どう影響を受けるかを示す。単一対象なら名前、複数なら**件数**を示す
- **ボタンは結果を表す動詞句**: 「はい / いいえ」でなく「ファイルを削除」「ファイルを保持」
- **既定値を「はい」にしない**（既定を置かないのが最善）
- 最も危険で稀な操作には、**普段しない操作**を求める（例: メーリングリストの削除前に DELETE と入力）。頻繁に使うと新たな標準になって自動反応を招く
- 詳細は段階的開示（「詳細を見る」）にして、本文は短く
- 定型的な確認は「今後表示しない」を選べるようにする（教育目的の確認は一時的）
- 警告の閾値は文脈で調整する（例: 普段の支払額の2倍を超える振込だけ確認）

## 3. 取り消し（Undo）— 確認より優先

| | 確認ダイアログ | Undo |
|---|-------------|------|
| タイミング | 実行の前 | 実行の後 |
| 役割 | 誤操作を未然に防ぐ | 誤操作から回復する |
| 副作用 | 多用すると注意力を損なう | 作業を妨げない |

- 確認だけでは防げない誤りが残るため、**Undo を可能な限り提供する**（NN/g）
- 取り消せない操作の代わりに、**一定期間のバックアップや「ゴミ箱」**を残すのが望ましい（NN/g の例: 削除確認よりバックアップ）
- 実装案（経験則）: 削除は論理削除 + 一定期間後に物理削除、完了メッセージに「元に戻す」を付ける

## 4. エラーメッセージ

NN/g の14項目の要点:
1. **欄の近くに**表示する（近接で、メッセージと対象の関係が分かる）
2. 目立たせる（太字、高コントラスト、赤）。メッセージと、直す対象の両方に適用
3. **色以外の手がかり**を併用（アイコン、枠線、テキスト）
4. **深刻度に応じた表示**: 軽い注意はラベル・トースト・バナー、作業を止める重大なエラーだけモーダル
5. **操作途中の探索をエラー扱いしない**（空欄で離れただけなど）。ミスが起きやすい入力にはリアルタイム検証を検討
6. 平易な言葉。専門用語・略語を避け、エラーコードは診断用に限る
7. **具体的に**説明する。「エラーが発生しました」は避ける
8. **解決策を示す**（対処法、次にできる行動）
9. **非難しない**: 「無効」「不正」「誤り」のような責める語を避ける。ユーモアも避ける
10. **入力内容を保持**し、最初からやり直させない
11. 修正の手間を減らす（正しそうな候補を小さなリストで提示）
12. よくあるミスを事前に警告
13. 仕組みの説明は簡潔に。詳しくはリンクで
14. システム全体の障害では、お詫びに意外性や遊び心を加えてもよい（稀な場合のみ）

文言の例（経験則）:
- 悪い: 「入力値が不正です」 → 良い: 「メールアドレスに @ が含まれていません。例: name@example.com」
- 悪い: 「権限がありません」 → 良い: 「この操作には管理者権限が必要です。権限の申請は〇〇から」

## 失敗例

- すべての削除に確認を出して、利用者が読まずに押す
- 「OK / キャンセル」だけで、何が起きるか分からない
- 削除が即時・不可逆で、Undo もゴミ箱もない
- 「エラー 500」を利用者に見せる
- エラーで入力が消える
