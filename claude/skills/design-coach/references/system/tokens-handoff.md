# トークン・コンポーネント・実装への引き渡し

確認状況: W3C Design Tokens 仕様（ドラフト）、Tailwind CSS v4 のテーマ変数、Atomic Design（Brad Frost）、デジタル庁DSのスタイル名の構成を取得して確認済み。引き渡し手順そのものは、これらを組み合わせた私の整理（経験則）。

## トークン（定数化）

デザインの値（色・文字・余白・角丸・影・時間）を、**役割で名前を付けた変数**にする。値を直書きしない。

### 命名
- 値でなく**役割**で付ける: `color-text-muted`、`color-surface`、`space-4`。「`gray-500` の文字色」でなく「補助テキスト色」
- 段階（色の階調、余白のスケール）は、基本値の層に。**役割の層（セマンティック）が基本値の層を参照**する（エイリアス）。ダークテーマは、役割の層の参照先を差し替える
- デジタル庁DSの例: テキストスタイルを「種類-サイズ-太さレベル-行高」で命名（例: `Std-17N-170`）

### W3C Design Tokens 仕様（ドラフト）
- JSON でトークンを交換する形式。`$value` が必須。型は `$type`（`color`、`dimension`（px/rem）、`fontFamily`、`fontWeight`、`duration`（ms/s）、`cubicBezier`、`number`、複合型の `typography`、`shadow` など）
- 値を持たないオブジェクトは**グループ**。`$type` をグループに付けると配下の既定の型になる
- **エイリアス**は `{group.token}` で参照。循環参照は禁止
- **成熟度: Community Group の preview draft（W3C 標準ではない）。実装や直接の参照は避けるよう明記されている**（2025.10 版）。ツール間の交換形式として注視するが、採用は慎重に

### Tailwind CSS v4（CSS 変数ベース）
- `@theme` ディレクティブ内に**テーマ変数**を定義すると、対応するユーティリティクラスも生成される（`--color-mint-500: oklch(0.72 0.11 178);` → `bg-mint-500`）
- 名前空間: `--color-*`、`--font-*`、`--text-*`、`--font-weight-*`、`--tracking-*`、`--leading-*`、`--breakpoint-*`、`--spacing-*`、`--radius-*`、`--shadow-*`、`--ease-*`、`--animate-*` など
- `--color-*: initial;` で名前空間の既定値を全て削除、`--*: initial;` で既定テーマを全て無効にして、**独自のトークンだけ**にできる
- 他の変数を参照するなら `@theme inline`。使われていなくても全て出力するなら `@theme static`
- テーマ変数は通常の CSS 変数（`var(--color-mint-500)`）としても使える
- ユーティリティに結びつけない変数は `:root` に書く。テーマ変数は**トップレベル必須**（セレクタやメディアクエリの内側に入れられない）

## コンポーネント（Atomic Design）

| 段階 | 内容 |
|------|------|
| Atoms | これ以上分けると機能を失う最小要素（ラベル、入力欄、ボタン） |
| Molecules | atoms の組み合わせ（ラベル + 入力欄 + ボタンの検索フォーム） |
| Organisms | ページ内の独立したセクション（ヘッダー、商品一覧グリッド） |
| Templates | レイアウトにコンポーネントを置いた骨格 |
| Pages | テンプレートに実コンテンツを入れた具体例 |

使い方（原著）:
- **段階を順に進める工程ではなく、同時並行のメンタルモデル**。部分と全体を行き来する
- 要素を単独で完成させてから組み立てない。全体で機能するかを確かめながら作る
- **Pages で実コンテンツを入れて検証**し、問題があれば該当する molecule まで遡って直す。表示のバリエーション（カートの商品数、権限の有無）も Pages で定義する
- 名称は組織の文化に合わせて変えてよい。**厳格なドグマではない**
- 見た目より先に**コンテンツの構造**を考える
- CSS/JS の設計手法とは別物。UI の設計システム全体の話

## 実装への引き渡し（specify モードの出力）

design-system.md には、実装側がそのまま使える形で次を記す（経験則）:

1. **トークン一覧**: 役割名 + 値（色は OKLCH または hex、余白は px/rem、時間は ms）。ライト/ダークの両方
2. **テキストスタイル**: サイズ・行高（単位なし）・ウェイト・字間
3. **コンポーネントごとの状態**: 通常 / hover / focus / active / 無効 / エラー / ローディング / 空
4. **アクセシビリティ要件**: コントラスト比の実測値、最小ターゲットサイズ、フォーカス表示（`a11y/wcag.md`）
5. **動き**: 時間と イージング、`prefers-reduced-motion` での置き換え（`motion-interaction.md`）
6. **実装のフレームワーク別の落とし方**（例: Tailwind v4 なら `@theme` にトークンを定義）

## エンジニア向け対応表

| デザイン | 近い概念 |
|---------|---------|
| トークン | 定数 / 設定値（役割で名前付け） |
| エイリアス | 定数が別の定数を参照 |
| コンポーネントの状態 | 型の取りうる値（網羅しないとバグになる） |
| Atomic Design | 小さな関数から合成する設計（ただし厳格な階層ではない） |
