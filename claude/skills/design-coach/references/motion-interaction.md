# モーション・インタラクション

上質に見えるサイトの差の多くは、静止画ではなく**動き**にある。ただし実装コストと失敗リスクが高いため、目的と範囲を決めてから使う。

## 目的で選ぶ

| 目的 | 例 |
|------|----|
| 状態の理解 | 開閉、タブ切替、ページ遷移、エラーの出現 |
| 注意の誘導 | 重要要素の登場、スクロールによる順次表示 |
| 触感・上質さ | ボタンの押下、ホバー、カーソル追従（控えめ） |
| 世界観 | ファーストビューのスライド、背景の緩やかな動き |

目的のない動きは入れない。

## 時間とイージング

| 種類 | 時間 | イージング |
|------|------|-----------|
| 簡単なフィードバック（チェックボックス、トグル） | 約100ms | ease-out |
| モーダルの表示など画面が大きく変わる | 200〜300ms | ease-out |
| ポップアップの出現 / 退場 | 約300ms / 200〜250ms | ease-out（退場は ease-in も可。出現を退場より少し長く） |
| 大画面での大きな移動 | 〜400ms（上限の目安） | ease-out |
| 500ms 以上 | 遅く感じ、煩わしい（NN/g）。ファーストビューのスライドなど意図した演出に限る | - |

- 同時に動かす要素は**ずらして順に**すると雑に見えにくい（経験則）
- 動く距離は小さく（12〜24px）。大きく動かすと酔いや遅延感の原因になる

## 実装方針（実装は別途依頼。ここでは設計を決める）

- 動かすプロパティは `transform` と `opacity` が基本（レイアウトを揺らさない）。ただし NN/g は、多くの環境で不透明度の変化は計算負荷が高く、多数を同時に変えると滑らかさが落ちうると指摘する。イージングは **ease-out が基本**、等速（リニア）は避ける。仕様は動画だけでなく ms 単位のタイムラインで渡す
- スクロール連動は IntersectionObserver で「一度だけ」表示。毎回再生しない
- 全画面スライドは、キーボード・タッチ・ボタンの全てで操作でき、**現在位置と枚数（例: 1 / 3）を表示**する
- 自動再生は停止ボタンを付ける。最低でも一時停止できるようにする
- 重いライブラリ（スクロールアニメーション系）は、必要性を示してから採用する。軽量な CSS だけで足りることが多い

## アクセシビリティと負荷

- `prefers-reduced-motion: reduce` では、動きを**減らす・やわらかいものに置き換える**（例: スケールの動きを不透明度の変化に）。進捗表示など、情報伝達に必要な動きは残すか代替を用意する（MDN）
- 点滅（毎秒3回以上）はしない
- モバイルでは負荷を下げる（パララックスや動画背景は原則外す、または静止画に差し替え）
- ローディング中の見せ方（スケルトン、プログレス）を決める

## モックでの扱い

- explore モードのモックには、**代表的な動き1〜2個だけ**入れる（実装できる範囲に限る）
- 動きの仕様は、`design-system.md` にトークン（時間・イージング）として記録し、実装側に渡す
- モックで作れない複雑な動き（スクロール連動の演出など）は、文章と参考サイトで仕様化し、「実装難度: 高」と明記する

## よくある失敗

- すべての要素がフェードインして、何を見ればよいか分からない
- 動きが遅い（待たされる）、または速すぎて見えない
- 動きの時間・イージングが場所ごとにばらばら
- 動かない環境（reduced-motion、低スペック）で内容が見えない
