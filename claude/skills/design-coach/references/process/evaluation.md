## ヒューリスティック評価（専門家による点検）

利用者を使わずに、10のヒューリスティクス（`theory/heuristics.md`）を基準に、画面を点検する手法。

手順（NN/g）:
1. **準備**
   - 評価者は**3〜5人**が理想。1人では見落としが出る
   - 全員がヒューリスティクスを読む。初回は簡単なデザインで練習する
   - **範囲を絞る**（タスク、画面、ユーザーグループ、デバイスのどれか）
   - 他の評価者の結果は、各自の評価が終わるまで見せない
2. **個別評価**（1人 1〜2時間）
   - 1回目: 評価せず、タスクを通して操作して慣れる
   - 2回目: 10のヒューリスティクスに違反する箇所を探し、問題点と改善案を記録する
   - 違反＝必ず修正が必要、ではない。文脈と代替案で判断する
3. **統合**
   - 類似の問題をグループ化する（付箋やホワイトボード）
   - 議論して、体験への影響、事業目標への影響、追加データが必要な問題、次のテストで優先する問題を決める
   - 重大度の数値による採点は、NN/g の記事に記載がない。**チーム議論で優先度を決める**

本スキルの批評モードは、1人の評価者としてこの手順に近い（重大/中/軽微の3段階は私の整理）。複数の視点が要る場合は、ユーザーや同僚の評価を併用する。

## ユーザビリティテスト

実際の利用者（または近い人）にタスクを依頼し、行動を観察する手法。

- **3つの要素**: ファシリテーター（進行。参加者を誘導しない）、タスク（現実的な活動。**文言で結果が変わるので慎重に**）、参加者（実際の利用者か、近い背景の人）
- 手順: 計画とタスク作成 → タスクの提示（声に出して読んでもらう） → 観察と傾聴 → 事後の深掘り質問 → 分析と改善案
- **思考発話法**（考えていることを声に出す）で、行動の背景を把握する
- 定性テスト: 問題の発見が目的。**単一の利用者グループなら約5人**で多くの一般的な問題が分かる
- 定量テスト: タスク成功率と所要時間などの指標でベンチマークを取る。**20人**程度が推奨（NN/g の別記事の記載）
- 形式: 対面、リモート（モデレーション型）、リモート（非モデレーション型）

### 5人でテストする根拠

- 発見できる問題の割合は N(1−(1−L)ⁿ)。L は1人で見つかる割合（通常 **31%**）。**5人で約85%**。以降は同じ問題の繰り返しが増える
- **15人を1回より、5人を3回**に分ける。1回目で見つけて直し、2回目で効果と残りを確認し、3回目で深い構造の問題へ。修正で新たな問題が生じることもあるため、繰り返す
- 例外: 性質の大きく異なる利用者グループがあるときは、グループごとにテスト（2グループなら各3〜4人、3グループ以上なら各3人）。カード分類は15人
- 1人だけでは、偶発的・非典型的な行動に惑わされる

## 使い分け

| 段階 | 手法 |
|------|------|
| 方向性の探索 | モックを見せて、ヒューリスティック評価、数人にテスト |
| 実装前 | ワイヤ/モックでユーザビリティテスト（5人×反復） |
| 実装後 | 実装物でのユーザビリティテスト、アクセシビリティの確認（`a11y/wcag.md`） |
| 運用中 | アクセス解析で気づき、ユーザビリティテストで理由を確かめる（解析だけでは意図が分からない） |
