# 探索モード

方向性を2〜3案、HTMLモックで見せて選んでもらう。言葉だけでは判断できない「見た目の方向」を決めるためのモード。

## 一任モード

ユーザーが「おまかせ」「全て任せる」「好きに進めて」と言ったときは、**判断の権限が委ねられている**。手順1・2の確認で止まらない。

- 未確認の項目（FEEL / ANTI-FEEL、色・フォントの制約、素材の有無、動きの水準、保存先）は、依頼内容から導いた仮説で埋め、**「採用した前提」として提示の冒頭に明示する**
- 聞くのは、外れると手戻りが大きい論点だけ（ブランド名、既存のロゴ・ブランドカラー、法的な制約、予算・工数の上限）。会話に出ていれば聞かない
- 「探索から仕様化まで進めたい」のように、仕様化までの進行が依頼文に含まれている場合は、推奨案での仕様化へ進む明示的な許可として扱う。ただし、依頼文に「確認したら次へ」「あなたが確認したら」など確認の段取りが書かれているときは、仕様化の後に確認を挟む（仕様化までは進めてよく、次のスキルの起動の前に止まる）
- 一任でも、提示（手順5）の「推奨・理由・外した理由」は省略しない。好みはユーザーに固有なので、**推奨は覆される前提で出す**（ユーザーが選ぶ・覆す手段を残す）
- 実行の記録（依頼の原文、採用した前提、成果物の索引）を、プロジェクトの `test-record/` など、ユーザーが指定した場所に残す。指定がなければ保存先を1つだけ提案する

## 手順

1. **前提の確認（最大4問、まとめて1メッセージ。一任モードでは省略し、仮説を前提として明示する）**
   - 何の画面か・誰が使うか
   - FEEL 3語 / ANTI-FEEL 3語
   - 色・フォントの制約（ブランドカラー、避けたい色）
   - 参考デザイン（任意）
   - 動きのある画面なら、動きの水準（CSS中心 / ライブラリ / WebGL）と素材の有無（`references/assets-and-limits.md`）
   既に相談モードで出ている情報は聞き直さない。
   WAIT_FOR: ユーザーの回答（一任モードでは待たない）

2. **保存先の確認**（出力形式が自明でないため。一任モードでは既定を採用して報告する）
   - 既定の提案: `<プロジェクト>/.design/explore/`（craft プロジェクトなら `.craft/docs/explore/`）
   - プロジェクト外の相談なら、保存先をユーザーに聞く
   WAIT_FOR: ユーザーの回答（一任モードでは待たない）

3. **案の設計**: 案同士は**意図的に離す**（色相だけ変えた似た案を作らない）。次の軸のうち2つ以上を変える。
   - 密度（ゆったり / 引き締め）
   - 形（直線・シャープ / 丸み・柔らかい）
   - タイポ（セリフ / サンセリフ / 個性的ディスプレイ）
   - 色の大胆さ（モノトーン+1色 / 多色）
   - 構図（対称 / 非対称・大胆なスケール差）
   各案に名前と1行コンセプト、使うアーキタイプ（`design-brief.md` テンプレートの表）を付ける。
   **3案のうち1案は、用途で求められる「目を引く強さ」を最大にした大胆な案にする**（抑制・上質寄りの案だけで揃えない。AI は無難で抑制した案に寄りやすい）。

4. **モック作成**: 案ごとに1つの自己完結HTML（`mock-A.html` など）。
   - 対象は代表的な1〜2画面分のみ（LPならファーストビュー+1セクション、業務系なら一覧+フォームの一部）
   - CSS変数でトークン化し、色・フォント・余白の値が読み取れるようにする
   - フォントは `references/typography.md` の「配布条件を確認できる候補」から選ぶ。外部フォントを使う場合はGoogle Fontsなど公式配布を使う
   - ダミーテキストに `lorem ipsum` を使わず、実際の用途に近い文言にする
   - 動きは代表的な1〜2個だけ入れる。**各動きに「実装難度（低/中/高）」と「`prefers-reduced-motion` の代替」を注記**し、モックで作れない動きは文章と参考で仕様にする（`references/motion-interaction.md`）
   - 行高・サイズは `references/ja/typesetting.md`（デジタル庁DS）に従う: 本文・UI は 16px 以上（本文 16〜17px は行高 1.7〜1.75、見出しは 1.4〜1.5）。14px は、タグ・キャプションなど限定的な用途のみ。見出しだけ詰める場合は理由を書く
   - モックでも守る最低限（自作モックの検査で出た問題）: 見出し `h1` の中に補足文を入れない。共通クラス（左右余白など）を、別のセレクタの `padding` / `margin` 省略記法で上書きしない（詳細度の衝突で余白が消える。個別方向は `padding-block` などを使う）。初期状態で `opacity:0` にする要素は、JS が動かないと見えなくなるため、JS 有効時のみ非表示にする。`aria-live` はスクロールで頻繁に変わる文言に付けない。`overflow:hidden` の固定高さの入れ物は、行間を広げると内容が切れる恐れ（WCAG 1.4.12）
   - モックは判断材料であり、実装には流用しない旨をファイル冒頭コメントに書く

   **自己点検**（提示前）:
   1. JS の構文（`mise x node@lts -- node --check`）、HTML タグの整合
   2. 主要な色の組み合わせのコントラスト実測（テキスト 4.5:1、非テキスト 3:1）。計算は `references/process/measure.md`
   3. **実ブラウザで、モックに含めた全セクションを確認する**（ファーストビューだけで済ませない。モックは代表的な1〜2画面分なので、LP 全体の検証は実装後に行い、提示に「未確認（モック外のセクション）」と書く）。簡易サーバーで開き、最初から最後までスクロールして各セクションを見る。`references/process/measure.md` の手順と `audit.js` を使い、次を実測する: 各セクションの見出しの左端 x 座標が揃っているか、`scrollWidth > clientWidth`（横スクロール）、本文サイズと基準未満の文字。モバイル幅（390px）は、同じ手順の `iframe` で確認する
   4. 共通の構造・CSS を持つ複数案は、**1案で全セクションを確認してから**他案に展開する（同じ不具合が全案に出るのを防ぐ）
   5. ブラウザ自動化が使えないときは、その旨と「全セクション・モバイル幅は未確認」を提示に明記する
   動きの実際の見え方・キーボード操作・スクリーンリーダーは、人が確認するまで未確認と明記する。起動したサーバーは、ポートで停止し、開いたタブを閉じる。

5. **提示**: 冒頭に「採用した前提」（一任モードのとき）。案ごとに「何を狙ったか」「トレードオフ」を各2行で比較表にする。**推奨案を1つ決め、理由と、他案を外した理由を必ず書く**（選択肢を並べるだけで判断をユーザーに戻さない。推奨はユーザーが覆せる形で出す）。
   推奨の評価軸は、**用途で変える**。広告LP・ポートフォリオ・ブランドの入口のように「一瞬で目を引く・記憶に残る」ことが成果になる画面は、目を引く強さと独自性を最優先する。コーポレート・業務系・信頼が要る領域は、可読性・一貫性・信頼を優先する。**推奨は無難（抑制・上質）側に偏りやすい**ので、最も大胆な案を外すときは、用途に照らした理由を書く（「地味になる」「素材がないと安く見える」だけで外さない）。自己点検で確認できた範囲と未確認を分けて示す。`open` コマンドでブラウザ表示してよいか確認してから開く（一任モードでは、仕様化の前に見せる機会を作るため、開いてよい旨を添えて提示する）。
   選択肢は番号リスト（A / B / C / 組み合わせ / ブラウザで開いて見てから決める / 自由記述）。「ブラウザで開いて見てから決める」が選ばれたら、`open` で3案を開き、**見終わった後の選択肢（案を選ぶ・修正する）をもう一度提示して待つ**（開いただけで次へ進まない）。
   WAIT_FOR: ユーザーの選択（一任モードで、ユーザーが「進めて」と明示したときは、推奨案で仕様化へ進む。選択は仕様化の後でも差し替えられるよう、`design-brief.md` の「8. 懸念・調整事項」に採用理由と他案を記録する）

6. 選択後、必要なら微調整（1往復まで）してから、仕様化（`modes/specify.md`）へ進むか確認する。

## 禁止

- 案が似ている状態で提示すること（作成後に自己点検し、似ていれば作り直す）
- 理由なき青プライマリ・グレーのみ・Interのみ
- モックを実装コードとして渡すこと

末尾に `使った原則:` を1行添える。
