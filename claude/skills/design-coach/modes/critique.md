# 批評モード

既存の画面を見て、問題点を優先度つきで指摘する。実装の修正は行わず、修正指示を出す。

## 入力の取得

- スクリーンショット画像 → Read で画像として確認する
- URL / ローカル開発サーバー → `mcp__puppeteer__puppeteer_navigate` → `mcp__puppeteer__puppeteer_screenshot`。使えなければ Chrome 自動化ツール。`file://` は開けないため、`python3 -m http.server <port> --bind 127.0.0.1` で配信する（終了後に停止）
  - 実測（フォントサイズ、ターゲット、コントラスト）の手順は `references/process/measure.md`
  - Puppeteer MCP が使えない場合は、その旨を伝えてスクリーンショットの提供を依頼する
  - 撮影は可能なら幅 1440 と 390 の2サイズ
- コードのみ（画面なし）→ 画面を見られない旨を伝え、スクリーンショットを依頼する。コードから推測する場合は推測と明示する

## 観点（この順で見る）

1. 階層: 一番大事な情報が最初に目に入るか。視線の流れは意図どおりか
2. 余白とグルーピング: 関連するものが近く、無関係なものが離れているか。余白の値に規則があるか
3. タイポ: ウェイト・サイズの差でレベルが区別できるか。行長・行間は適切か
4. 色: コントラスト比（本文 4.5:1 以上）、色の役割が一貫しているか、色だけに意味を持たせていないか
5. 整列: 左端・基準線が揃っているか
6. 状態: hover / focus / 無効 / エラー / 空 / ローディングの表現
7. レスポンシブ: 狭い幅で崩れないか、タップ領域（WCAG: 最低24px、重要な操作は44px）
8. 個性: `references/anti-generic.md` のチェック

観点ごとに該当する `references/` を必要な分だけ Read する（まず `references/INDEX.md`）。
画面構成は `ia/`、フォーム・テーブル等は `patterns/`、原理は `theory/heuristics.md` と `theory/visual-hierarchy.md`、数値基準は `a11y/wcag.md` と `ja/typesetting.md`。進め方は `process/evaluation.md`（ヒューリスティック評価）に近い。

## 出力形式

指摘は重大度で並べる。

```
[重大] 〜
  理由: （原則名）〜
  修正: 〜（具体値）
[中] 〜
[軽微] 〜
良い点: 〜（1〜3個。残すべきものを明示する）
```

- 重大: 目的の達成を妨げる（読めない、押せない、何が主役か不明）
- 中: 品質を下げる（不統一、余白の不規則）
- 軽微: 磨き込み

指摘は**最大12件**。同種の欠陥は1件にまとめる（例: 「文字の小ささとコントラスト」）。重大と中を優先し、軽微は1件にまとめ、溢れた分は「他に〜件」と見出しだけ列挙する（欠陥が多い画面で、10件の上限だと、数値の揃え・空状態などの具体的な指摘が落ちたため）。

## 修正の引き渡し

ユーザーが修正を求めたら、箇条書きの修正指示（対象 → 変更内容 → 具体値）にして、メインのClaudeに渡す。自分ではコードを書かない。

末尾に `使った原則:` を1行添える。
