# /runbook

## 使い方

- `/runbook <タスク名>` — 指定タスクのチェックリストを生成
- `/runbook` — 引数なしの場合はタスク名を自由入力で確認する

前提: bash（pwd/date/mkdir）が利用可能なこと。issue作成を行う場合は `gh` CLIが認証済みであること。

---

## 手順

### ステップ1: タスクの特定

```
IMPORTANT: タスク名の自由記述、およびステップ3の確認はすべてプレーンテキストの番号リスト形式で質問する。
PROHIBITED: AskUserQuestionツールを使うこと（呼び出し元の実行コンテキストによっては存在しない場合があるため）。

IF 引数でタスク名が指定されていない:
  OUTPUT（プレーンテキスト）:
    「何をしたいですか？どんな作業でも自由に教えてください。」
  GATE: WAIT_FOR: ユーザーの回答
  {task} = ユーザーの回答（複数作業・複合的な内容でもそのまま受け取る）

ELSE（引数でタスク名が指定されている場合）:
  {task} = 引数として指定された値
ENDIF
```

---

### ステップ1.5: ソースコードの調査

```
事前準備: Bash で `pwd` を実行し、絶対パスのカレントディレクトリを確定する
   （Bash呼び出し間でカレントディレクトリが保持されない実行環境があるため、
    以降の調査・パス解決はこの絶対パスを基準に行う）。

IMPORTANT: {task} の文中に複数のサービス・コンポーネント名（例: 「apiとworker」
「フロントとバックエンド」等、2つ以上の対象を並列に指示する表現）が含まれる場合、
調査範囲をカレントディレクトリ配下だけに限定せず、親ディレクトリ・兄弟ディレクトリ
（モノレポ構成の他パッケージ、infra/ 等の共有設定）まで広げて調査する。
  手順: 親ディレクトリで `ls` / `find -maxdepth 2` を実行し、{task} に登場する
  サービス名に対応するディレクトリと、docker-compose.yml 等の共有インフラ定義を探す。

カレントディレクトリ（複数サービスにまたがる場合は上記で広げた範囲も含む）の
ソースを調査して {context} を組み立てる。

調査手順:
  1. ls / find で構成を把握する
  2. {task} に関係しそうなファイルを読む
     - package.json / go.mod / requirements.txt / Gemfile → 言語・FW・依存
     - docker-compose.yml / Dockerfile / infra/ → インフラ・DB種別
     - .env.example / config/ / database.yml → 接続先・環境設定
     - migration/ / schema/ → 現在のDB構造
     - README / docs/ → 既知の注意事項
  3. 複数サービスにまたがるタスクの場合、各サービスのREADME/docsと共有インフラ定義に
     記載されたデプロイ順序・依存関係の記述を確認する
  4. 調査結果を {context} にまとめる:
       - 技術スタック（言語・FW・インフラ）
       - 現在のDB種別・接続方式
       - 移行対象のデータ規模（テーブル数・推定行数など、分かれば）
       - 複数サービス構成の場合、デプロイ順序・依存関係（README等に明記があれば）
       - その他 {task} に関係する情報

ソースが存在しない・{task} に無関係なら {context} = "" のままでよい。

調査後、コードから読み取れた内容を1〜3行で要約してユーザーに提示する。
その上で、コードから判断できなかった点のみをピンポイントで質問する。
IMPORTANT: {task} が本番/ステージング操作に関わる場合、接続先環境やデータ規模が
コードから判断できないときは必ず明示的に質問すること（推測で進めない）。
  例: 「package.json を確認しました。Next.js + Prisma 構成ですね。
       移行先の PostgreSQL はどの環境ですか？（本番 / ステージング）」
  例: 「docker-compose.yml に MySQL の記述がありました。
       本番環境のデータ量はどのくらいですか？」
質問した場合はGATE: WAIT_FOR: ユーザーの回答。質問がなければそのままステップ2へ進む。
```

### ステップ2: チェックリストの生成

```
CLASSIFY リスクレベル（{task} と {context}、ソース調査結果から判定）:
  HIGH   → 本番DB操作・本番デプロイ・大規模インフラ変更（判断に迷う場合はHIGHとして扱う）
  MEDIUM → ステージング操作・依存パッケージ更新・設定変更・機能フラグ操作
  LOW    → 開発環境作業・ドキュメント更新・ローカルテスト

リスクレベルに応じた追加ルール:
  HIGH   → ロールバック手順を必須とし、不可逆操作の直前に
           「[ ] 確認: 以下の操作は不可逆です。続行する」を挿入する
  MEDIUM → ロールバック手順を含める
  LOW    → ロールバック手順は任意

IMPORTANT: {task} が複数サービス・複数ディレクトリにまたがる場合、生成フォーマットの
「事前確認」に「関連する他サービス・共有インフラのREADME/runbookを確認し、
デプロイ順序や依存関係に矛盾がないことを確認した」という項目を必須で含めること。

生成フォーマット:
  # {task} チェックリスト — YYYY-MM-DD
  （YYYY-MM-DD はステップ3でBash実行後に実際の日付で置換すること）

  リスクレベル: <HIGH / MEDIUM / LOW のいずれか>

  ## 事前確認
  実行前に必ず確認する。条件が揃っていない場合は実行を中止する。
  - [ ] ...

  ## 実行手順
  順番通りに実行する。各ステップ完了後にチェックを入れてから次へ進む。
  - [ ] ...

  ## 完了確認
  すべてパスしてから完了とする。1つでも失敗した場合はロールバックを検討する。
  - [ ] ...

  ## ロールバック手順
  （HIGH / MEDIUM の場合のみ必須。問題発生時はここから逆順で復旧する）
  - [ ] ...

IMPORTANT: 表現ルール — 各チェックポイントは「何をするか」ではなく「何を確認したか」を、
対象操作に即した具体表現で問う形式にすること（曖昧な言い回しを避ける）。
  NG: 「DBバックアップを取る」
  OK: 「DBバックアップを取得し、ファイルサイズが0でないことを確認した」
  NG: 「必要に応じてロールバックする」
  OK: 「`migrate:rollback` を実行し、対象カラム/テーブルが変更前の状態に
       戻っていることを確認した」
  OK: 「ロールバック不要と判断した根拠（例: 追加のみでデータ欠損リスクなし）を記載した」
  生成指針: DO-CONFIRM方式（「〜した」という過去形で確認）・不可逆操作前は承認ゲートを挿入・ロールバック境界を明示すること
```

### ステップ3: 出力とファイル保存

```
チェックリストを会話上に出力する。

{コード変更あり} = チェックリストの実行手順にソースコードの変更（依存パッケージ変更・設定ファイル修正・
                   スキーマ変更・コード書き換えなど）が含まれる場合 true、それ以外 false

プレーンテキストの番号リストで確認する（ステップ1と同様にAskUserQuestionツールは使わない。自由記述の補足も許容する）:

  質問1: ファイルに保存しますか？保存する場合は保存先パスも一緒に教えてください。
    [1]: 保存する（保存先パスも記入）
    [2]: 保存しない

  IF {コード変更あり}:
    質問2: このタスクにはコード変更が含まれています。GitHubにissueを作成しますか？
           作成すると /issue-triage でPRまで進められます。
      [1]: 作成する
      [2]: 作成しない

    複数質問をまとめる場合は質問順のカンマ区切りで回答できる旨を添える。
      例: 質問1のみなら「1, ./scripts」、両方答えるなら「1, ./scripts, 2」
  ENDIF

GATE: WAIT_FOR: ユーザーの回答

{保存する} = 質問1の回答が「1」（保存する）
{保存パス} = 質問1の回答に含まれるパス
             （{保存する} が true でパス未記入の場合は「保存先パスを教えてください」と改めて聞く）
{issue作成する} = {コード変更あり} かつ 質問2の回答が「1」（作成する）

PROHIBITED: 上記GATEの回答を待たずにWriteツールを実行すること。

IF {保存する}:
  1. Bash で `date +%Y%m%d` を実行して日付を取得する
  2. チェックリスト内の YYYY-MM-DD を取得した日付（YYYY-MM-DD形式）で置換する
  3. ファイル名: runbook-{YYYYMMDD}.md
     同名ファイルが既に存在する場合は `date +%Y%m%d%H%M%S` で秒まで含めた名前にする
     例: runbook-20260603.md、重複時 → runbook-20260603143022.md
  4. {保存パス} が相対パスの場合は ステップ1.5で確定した絶対パスのカレントディレクトリと結合して
     絶対パスに変換する
  5. 指定パスが存在しない場合は Bash で mkdir -p <絶対パス> を実行してから保存する
  6. Write ツールで保存する（絶対パスを渡す）
     失敗した場合: 「保存に失敗しました。パスの権限を確認してください: <path>」と報告してSTOP
  7. Read ツールで {保存フルパス} を読み直し、チェックリスト本文が意図通り保存されていることを確認する
     内容が一致しない場合は再度Writeし直す（最大2回。それでも一致しない場合は手順6と同じ形式で失敗を報告してSTOP）
  8. 「`{保存フルパス}` に保存しました」と一言伝える
ENDIF
```

### ステップ4: コード変更が必要な場合のissue提案

```
{issue作成する}（ステップ3で確認済み）が false の場合: STOP

PROHIBITED: ステップ3のGATEで{issue作成する}が確認される前に本ステップの `gh issue create` を実行すること。

gh auth status を実行して認証状態を確認する。
IF 未認証、またはカレントディレクトリがGitHubリモートを持つgitリポジトリでない:
  「GitHubへの接続を確認できませんでした（gh認証または git remote を確認してください）」と報告してSTOP
ENDIF

HEREDOC で本文を渡し、シェル展開・コマンド破損を防ぐ:
  gh issue create --title "{task}" --body "$(cat <<'EOF'
  ## 概要
  {task} を実施する。

  ## 背景
  {ソース調査・ユーザー回答から得たコンテキストを簡潔に記載}

  ## やること
  チェックリストの実行手順のうち、コード変更が必要な項目を箇条書きで列挙する

  ## 参考
  runbook: {保存した場合はチェックリストのファイルパスを記載。保存しなかった場合は省略}
  EOF
  )"

作成したissueのURLを伝える。
「/issue-triage <issue番号> で対応できます」と案内する。
```
