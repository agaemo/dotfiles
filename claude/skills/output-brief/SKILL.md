# output-brief

```
SKILL_DIR      = このSKILL.mdが存在するディレクトリの絶対パス
SCRATCH_DIR    = 実行時のシステムプロンプトに記載されたスクラッチディレクトリ（案内が無い環境では /tmp）
RESEARCH_FILE  = {SCRATCH_DIR}/output-brief-research.md  （調査結果の一時ファイル）
OUTPUT_DIR_CANDIDATES = ./output/output-brief/ / ./docs/output-brief/ / ./tmp/output-brief/
  （最終成果物の保存先候補。いずれもカレントディレクトリ配下の相対パスで、ユーザーがGUIから直接開ける。`SCRATCH_DIR` のような絶対パスのスクラッチ領域は最終成果物の保存先にしない）
```

IMPORTANT: `RESEARCH_FILE` はステップ1〜3で使う内部調査メモであり、ステップ4で生成する最終成果物とは別物。処理を中断・終了する場合（後述の中断パスを含む）は必ず `Bash` で `rm -f "$RESEARCH_FILE"` を実行してから終える。

## 発動判断

以下のいずれかに該当する場合のみブリーフィングを行う。**全て指定済みなら即出力する（ステップ1〜3をスキップしてステップ4へ進む）。**

- 出力形式・保存先（HTML/Markdown/CSV/JSON × ファイル保存/Artifact公開/チャット表示の組み合わせ）が未指定、またはコンテンツ内容・構成が不明 → ステップ1で確認
- データ・素材が無い、または不十分・曖昧で調査が必要 → ステップ1で確認
- HTML でレイアウト・カラーが未指定 → ステップ2で確認

## フロー

### 質問の提示方法（共通ルール）

ユーザーへの確認・選択肢提示は `AskUserQuestion` ツールを使わず、**テキストの番号リスト**で行う:

```
[1]: <選択肢1>（必要なら補足）
[2]: <選択肢2>
[3]: <選択肢3>
```

複数の質問をまとめて聞く場合は、質問ごとに短い見出しを付けてから番号リストを並べる。
選択肢以外の自由記述を許す場合はリストの末尾に「その他: 自由に記入してください」を添える。
複数の質問をまとめて聞く場合は、回答形式の例を1行添える（例: `1,2,4:回答, 5` のように、質問順にカンマ区切りで、自由記述が必要な質問だけ `:テキスト` を続けてもらう）。
WAIT_FOR: ユーザーの返信（番号・選択肢のテキストいずれでも回答可）。

### 1. データ確認

指示から以下3点を把握する（発動判断でステップ1対象とした項目に対応）。**全て読み取れる場合はステップ2へ直行する。不明な点があれば番号リスト形式で1回にまとめて確認する:**

- 何を作るか（内容）
- データ・素材はあるか（URL・ファイルパス・テキスト）
- **出力形式・保存先**: 形式とその後の扱い（ファイル保存かArtifact公開か等）は組み合わせによって以降の質問（保存先パスの要否・Artifactの可否）が変わるため、切り離さず一体で確認する:
  ```
  [1]: HTML — ファイル保存
  [2]: HTML — Claudeでアーティファクトとして公開
  [3]: Markdown — ファイル保存
  [4]: Markdown — Claudeでアーティファクトとして公開
  [5]: CSV
  [6]: JSON
  [7]: チャット表示のみ
  その他: 自由記述
  ```
  出力形式が既に判明している場合、この7択を丸ごと出す必要はない。判明した経路は問わない（ユーザーの初期指示で直接指定されていた場合・後述の「その他」に自由記述で答えた場合のいずれも同様に扱う）。該当形式に対応する下記の分岐だけをいきなり確認すればよい。7択が必要になるのは形式自体が不明な場合のみ。絞った分岐リストに「その他」の自由記述枠は付けない（保存先はファイル保存・Artifact公開・チャット表示の3種類のみで、各分岐は既にそのうち該当する2択を提示しているため）。

  回答に応じて、続く保存先の扱いを分岐する（フォーマットが違えば「保存先」が意味する内容も変わるため、同じ質問テンプレートを使い回さない）:
  - `[1]``[3]`（ファイル保存）: 保存先パスが未指定なら、こちらから提案する。ユーザーに自由入力を求めるだけにしない:
    1. ファイル名を内容から1つ提案する（内容を表す2〜4語 + 出力形式に応じた拡張子。例: `sales-summary-2026-08-21.html`）
    2. `OUTPUT_DIR_CANDIDATES` の各ディレクトリと提案ファイル名を組み合わせ、番号リストで提示する:
       ```
       保存先:
       [1]: ./output/output-brief/<提案ファイル名>（推奨）
       [2]: ./docs/output-brief/<提案ファイル名>
       [3]: ./tmp/output-brief/<提案ファイル名>（一時的な確認用途）
       その他: 自由に記入してください（別のパスを指定）
       ```
    3. ユーザー指定のファイル名・パスがあれば1・2を省略しそのまま使う
  - `[2]``[4]`（Artifact公開）: 保存先パスという概念が無いため、この質問自体を行わずステップ2のレイアウト・カラー確認に直接進む
  - `[5]``[6]`（CSV/JSON）: 「ファイル保存 / チャット表示」の2択のみを確認する（Artifactは選択肢に出さない。CSV/JSONはArtifact非対応のため）
  - `[7]`（チャット表示）: 保存先の確認は不要
  - 形式がHTML/Markdown/CSV/JSON以外（PDF・プレーンテキスト等）と判明した場合（指示文で直接指定されていた場合・7択の「その他」に自由記述で答えた場合のいずれも含む）: Artifactとして公開可能な形式（HTML・Markdown相当）なら`[1]``[3]`と同様、それ以外なら`[5]``[6]`と同様に「ファイル保存 / チャット表示」の2択のみで扱う。判断基準はArtifact対応可否であり、内容の見た目や複雑さでは判断しない。
  - **唯一の例外**: ユーザーの初期指示だけで形式・保存先の一部しか判断できず、上記の番号リストを提示せず進んだ場合（発動判断で「全て指定済み」と誤って判定した等）は、ステップ2の直前で不足分をこの形式に沿って確認する。

**調査が必要な場合**

以下のいずれかに該当する場合は、ステップ2に進む前に `WebSearch` / `WebFetch` で調べる:

- データ・素材が指定されていない（「〜について調べて出力して」「〜を調査してまとめて」等）
- データ・素材はあるが、出力に必要な情報が不足している、または内容が曖昧（自分の知識だけでは出力内容の正確性に確信が持てない・指示文中の事実に最新情報の裏取りが必要・用語の定義が不明 等）

調査範囲が広く絞り込みが必要な場合や、情報源が乏しく方向性に迷う場合は、調査を始める前に番号リスト形式で対象・観点を確認する。
調査しても十分な情報が得られない場合は、その旨をユーザーに伝え、手がかり（URL・キーワード等）を追加でもらうか、不十分な情報のまま進めてよいか確認する。
調査結果は箇条書きやメモとして整理し、`Write` ツールで `RESEARCH_FILE` に保存する（Markdown形式）。
保存内容: 検索クエリ・参照URL・調査結果（箇条書き）・出典リスト。
Write に失敗した場合は調査結果をインメモリ（会話コンテキスト）で保持して続行する。
ステップ2以降では `Read` で `RESEARCH_FILE` を参照して内容を確認する。
手順・フロー・関係性など図解が理解を助ける内容が含まれる場合は、図解の追加も候補として検討し、ステップ2の確認に含める（詳細は後述の「図解・HTMLの詳細」参照）。

### 2. ブリーフィング

選択肢は「質問の提示方法（共通ルール）」の番号リスト形式で提示する（`AskUserQuestion` は使わない）。

#### 調査結果・出典の確認

ステップ1で調査した場合: `RESEARCH_FILE` を `Read` して調査内容を参照し、要約（出典・主要な事実を箇条書き）で提示する。「この内容で出力してよいか」「不足や見当違いがあれば指摘してほしい」と確認する。
調査結果に手順・フロー・関係性などが含まれ図解が理解を助ける場合は、図解の追加を提案し、含めるかどうかを同じ番号リストでまとめて確認する（図解の実装詳細は後述参照）。

出典リンクの確認は調査した場合に限らない: データ・素材にURL・リポジトリ等の出典がある場合（ユーザー指定URLや会話内で既に参照済みの外部情報も含む）、出典リンクを出力本文に参考リンクとして含めるか、不要かを番号リストで確認する。出典が明らかに存在しない場合（ユーザー提供のテキストのみ等、自明に不要な場合）は確認を省略してよい。

保存先パスなど他に未確定の項目がある場合は、同じ番号リストでまとめて確認する。
WAIT_FOR: ユーザーの確認。修正・追加調査の指示があれば反映してから先に進む（最大3ラウンド。収束しない場合は番号リスト形式でユーザーに方向性を確認し、指示があれば再開、なければ中断する）。

#### 図解・HTMLの詳細

**図解（Mermaid/viz-*）を含めることが決まった場合、または出力形式がHTMLの場合**、`$SKILL_DIR/references/html-and-diagrams.md` を `Read` して、レイアウト選択・カラー選択・図解の実装手順に従う。

CSV/JSON/プレーンMarkdown（図解なし）の場合はこのファイルを読む必要はない。

#### Markdown の場合

番号リストで以下を確認する:

- **見出し構造**: フラット（H2 のみ）/ 階層あり（H2 + H3）
- **テーブル**: あり / なし
- **コードブロック**: あり / なし

#### CSV の場合

番号リストで以下を確認する:

- **区切り文字**: カンマ / タブ
- **ヘッダ行**: あり / なし
- **文字コード**: UTF-8 / Shift-JIS

#### JSON の場合

番号リストで以下を確認する:

- **構造**: 配列 / オブジェクト（キーあり）
- **インデント**: あり（2 スペース）/ なし（minified）

#### その他のフォーマット

形式・主要構成（セクション・項目）を列挙して確認する。不明点は 1 回でまとめて質問する。

### 3. 承認・修正

ユーザーの承認を求める前に、選択内容を以下の形式で要約して提示する:

```
- 形式: <HTML / Markdown / CSV / ...>
- レイアウト: <layout>（HTML の場合）
- カラー: <color>（HTML の場合）
- 図解: <viz-*コンポーネント / Mermaid図 / なし>（含める場合）
- 保存先: <ファイルパス / チャット表示 / Artifact公開>
```

WAIT_FOR: ユーザーの承認（「OK」「はい」「進めて」等）を受けてからステップ4へ進む。
**PROHIBITED: 承認なしにステップ4（出力・保存）を実行すること。**
修正を求められた場合は、変更したい項目（レイアウト / カラー / 形式 / 保存先）を確認してから該当するステップに戻って再提示する（最大3ラウンド。収束しない場合は番号リスト形式でユーザーに方向性を確認し、指示があれば再開、なければ中断する）。

### 4. 出力

ステップ2で確認した形式・レイアウト・カラー等の選択を参照してアウトプットを生成する。

- ファイル保存の場合:
  1. `Bash`（`test -e <path>` 等）で既存ファイルの有無を確認し、存在する場合は上書きするか別名にするかをユーザーに確認する
     WAIT_FOR: ユーザーの選択
     **PROHIBITED: 確認なしに既存ファイルを上書きすること**
     別名を選んだ場合: 新しい保存先パスをユーザーに確認してから保存を続行する
     WAIT_FOR: 新しい保存先パスの回答
  2. Write ツールで保存し、ファイルの存在を確認してからパスを報告する
  3. HTML の場合は「ブラウザで開きますか？」と確認する
     WAIT_FOR: ユーザーの承認
     承認されたら `Bash` で OS に応じたコマンドを実行する
     （macOS: `open <path>` / Linux: `xdg-open <path>` / Windows: `start <path>`）
- チャット表示の場合: コードブロックで出力する
- Artifact公開の場合:
  0. **IMPORTANT: `Artifact` ツールを呼び出す前に、必ず `artifact-design` スキルを読み込むこと。** HTML・Markdownいずれもこのスキルの設計指針でファイルを書いてから発行する（Artifactツールの必須手順）。
     内容が入力の保存・状態の記憶・ライブデータの参照など静的HTMLでは完結しない機能を必要とする場合は、`artifact-capabilities` スキルも読み込んでから実装する（該当しない読み物系のページでは不要）。
  1. **PROHIBITED: 外部CDNへの依存（Mermaid.js等の`<script src="https://...">`、Google Fonts等の外部`<link rel="stylesheet">`、fetch/XHR）を含めること。**
     ArtifactはCSPで外部ホストへの通信をブロックする。外部scriptの読み込み失敗は他のスクリプト初期化まで巻き添えで止める場合があり（Mermaid図を含める場合の対応は `references/html-and-diagrams.md` 参照）、外部stylesheetもCSP違反としてブロックされる（fallbackはするが、コンソールにエラーが残る）。
     `assets/samples/` のテンプレートにある `<link rel="preconnect">` / Google Fonts の `<link>` タグは削除し、`font-family` は `system-ui` 以降のフォールバックのみで運用する。
     既知の制約: `slide` レイアウトの全画面表示ボタンは、Artifact環境（iframe）ではブラウザのPermissions PolicyによりFullscreen APIが使えず動作しない。テンプレートは `document.fullscreenEnabled` を見て自動的にボタンを非表示にする作りになっているため追加対応は不要。
  2. Artifactは既定で非公開（自分のみ閲覧可）だが、claude.ai上にホストされる旨を伝えて確認する
     WAIT_FOR: ユーザーの承認
     **PROHIBITED: 承認なしにArtifactツールを実行すること**
  3. `Artifact` ツールで発行する（`file_path` に生成したHTML/Markdownファイルのパス、`description` に内容を要約した1文、`favicon` に内容に合う絵文字1〜2個を指定）
  4. 発行されたURLを報告する
  5. 同じ内容の更新を求められた場合は、同じ `file_path` で再度 `Artifact` を呼び出す（同一URLに再デプロイされる）
- 保存に失敗した場合: エラーを報告し、別のパスをユーザーに確認する
- `RESEARCH_FILE` が存在する場合: `Bash` で `rm -f "$RESEARCH_FILE"` を実行して一時ファイルを削除する
