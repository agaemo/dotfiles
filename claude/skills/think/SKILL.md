# think — 思考・分析オーケストレーター

問いや相談を受け取り、内容に合った**カテゴリ**と **verbosity**（ひと言/箇条書き/フル）を判定して
サブスキルに委譲する。

```
SKILL_DIR = スキル起動時に提供される "Base directory for this skill:" のパス
```

## サブスキル一覧

| カテゴリ | スキル | 説明 | 手法名 |
|---|---|---|---|
| 対話 | dialogue | 方向性がまだ無い曖昧な相談に、問いを重ねて壁打ちする | ソクラテス式問答法 / GROWモデル |
| 構造化・伝達 | structure | 頭の中を整理して人に伝わる形にする | ロジックツリー / ピラミッドストラクチャ |
| 原因を掘る | root-cause | 「なぜ？」を繰り返し根本原因を掘り下げる | 5つのなぜ |
| 決める・比較する | decide | 選択肢のメリット・デメリットを整理する | Pros Consリスト |
| 多角的に検証する | six-hats | 提案・計画・選択肢を6つの視点で検証する | Six Thinking Hats（6視点分析） |
| アイデアを出す | idea | 新しい案・改善案を発想する | ブレインストーミング / 5W1H（対象があればSCAMPER） |
| 振り返る | reflect | 経験・期間を次に活かす形で振り返る | KPT |
| 矛盾を解消する | triz | 相反する要件を両立させる解決策を探す | TRIZ（発明原理） |

**注**: このテーブルを唯一の情報源とする。エラーメッセージ・未分類表示・確認テンプレート・手法名の提示は、ここに新しいスキルを追記すれば自動的に反映される想定で書くこと。他の箇所に個別のスキル名リスト・手法名リストをハードコードしない。

他の切り口を探したい場合は `{SKILL_DIR}/frameworks-reference.md` を参照する（サブスキル化されていない125個のフレームワーク一覧）。

## ステップ1: 引数の解析

引数の先頭がサブスキル名と一致するか確認する。

- **`/think <スキル名> <入力>`**: スキルを明示指定。`<入力>` を `{input}` とし、ステップ3の該当スキルへ直接委譲する
  - `<入力>` が空 → ここで汎用質問はしない。`{input}` = "" のままステップ3に進み、委譲先スキルの「引数なし」分岐（各スキルが用意する専用の質問文）に判断を委ねる
  - スキル名が存在しない → 「スキル名 `<X>` は存在しません。使えるスキル: {サブスキル一覧テーブルの各行のスキル名をスラッシュ区切りで列挙したもの}」と返してSTOP
- **`/think <入力>`**: スキル名なし。`<入力>` 全体を `{input}` としてステップ2に進む
- **`/think`（引数なし）**: 以下を表示して WAIT_FOR: ユーザーの返答

  ```
  何を壁打ちしたいですか？

  今どの段階ですか:
  - まだモヤモヤ（何から考えればいい？）
  - 方向性はある（深めたい）
  - 案はある（検証・評価したい）
  ```

  返答を `{input}` とし、選択した段階をカテゴリ判定のヒントとしてステップ2に進む。「まだモヤモヤ」→ステップ2のカテゴリ判定でdialogueを優先候補として検討する（他カテゴリの条件に明確に一致しない限りdialogueとする）。「方向性はある」→ステップ2の通常判定（ヒントなし）に委ねる。「案はある」→ステップ2のカテゴリ判定でsix-hats・decideを優先候補として検討する（該当条件を満たす方を選ぶ）。

## ステップ2: カテゴリと verbosity の判定

### verbosity の判定

`{input}` に以下が含まれる場合:
- 「ひと言」「さっと」「手短に」「手軽に」→ `{verbosity_label}` = ひと言、`{verbosity}` = 簡潔
- 「詳しく」「丁寧に」「しっかり」→ `{verbosity_label}` = フル、`{verbosity}` = 詳細
- それ以外 → `{verbosity_label}` = 箇条書き、`{verbosity}` = 標準

**注**: サブスキルには `{verbosity}`（簡潔/標準/詳細）を渡す。`{verbosity_label}` はユーザー表示専用。

### カテゴリの判定

**注**: 複数のカテゴリに同時該当する場合は「対話 > 目的が明確なもの（root-cause/decide/six-hats/reflect/triz） > 構造化 > アイデア出し」の優先順位で判定する（曖昧さが残る場合ほど、答えを急がず整理する対話寄りに倒す）。

**対話 / dialogue（以下を満たす場合）**
- 本人の中で答え・方向性・目標がまだ定まっていない曖昧な相談
- 「なんとなくモヤモヤする」「頭の中を整理したい」が目的で、以下のいずれにも該当しない
- 事実質問・比較質問（答えが一意に定まるもの）はここに該当しない → 直接回答する

**原因を掘る / root-cause（以下を満たす場合）**
- 「なぜ〇〇なのか」「本当の原因は何か」という根本原因への疑問がある
- 表面的な対処ではなく、繰り返し起きる問題の元を掘りたい

**決める・比較する / decide（以下を満たす場合）**
- 2つ以上の具体的な選択肢があり、それぞれの良し悪しを整理したい
- 「AとBどちらがいいか」という軽量な比較が目的（1つの提案の多角的リスク検証は six-hats）

**多角的に検証する / six-hats（以下を満たす場合）**
- 具体的な提案・計画・選択肢が含まれている
- 「検証したい」「評価したい」「リスクを洗い出したい」「良し悪しを整理したい」が目的

**振り返る / reflect（以下を満たす場合）**
- 過去の期間・出来事・経験の振り返りが目的
- 「うまくいったこと・課題・次に活かすこと」を整理したい

**矛盾を解消する / triz（以下を満たす場合）**
- 「〇〇するとXが悪化する」「両立できない」「相反する要件がある」という矛盾・トレードオフを含む
- 妥協でなく矛盾そのものを解消したい

**構造化・伝達 / structure（以下を満たす場合）**
- 頭の中がごちゃごちゃした話・考えを整理したい
- 人に説明・報告するために結論から筋道立てて伝えたい

**アイデアを出す / idea（以下を満たす場合）**
- 「アイデアを出してほしい」「何かないか」「案を考えてほしい」「提案してほしい」
- 新しいアイデア・解決策の生成、または既存対象の変形・発展が目的

## ステップ3: 委譲

**注（共通定義）**: 以下のいずれの委譲でも、選択スキルの `{SKILL_DIR}/<スキル名>/SKILL.md` を READ し、`{input}` と `{verbosity}` を渡して実行する。READ に失敗した場合（ファイルが存在しない等）は「スキル `<X>` を起動できません」と伝えてSTOPする。以下の各分岐では「委譲する」とのみ記す。

### スキル名を明示指定した場合（ステップ1で直接委譲）

IMPORTANT: 確認なしに即座に実行する。`{input}` が空でない場合はステップ2の verbosity 判定ロジックに準じて `{input}` から判定する。`{input}` が空の場合は一旦 `{verbosity}` = 標準 とする。委譲先スキルの「引数なし」分岐に従って質問し、ユーザーから実際の入力を得た時点で、（委譲先スキルにではなく）このスキル自身のステップ2の verbosity 判定ロジックをその入力に適用し直し、`{verbosity}` を更新してから委譲先スキルの以降の処理を続ける。

委譲する（上記共通定義の通り）。

### 自動判定した場合（ステップ2を経由）

`[{category_label}]` ＋ 説明1文の形式で提示し、確認する。`{category_label}` = サブスキル一覧テーブルの「カテゴリ」列の値（例: 対話、構造化・伝達）。

```
[{category_label}] <手法名> — <何をする手法か一言>
粒度: {verbosity_label}

このまま進めますか？ [yes / 別の方向で / 直接回答して / <別スキル名>]
```

`{手法名}` はサブスキル一覧テーブルの「手法名」列の値を使う（著者名・年は含めない）。

`[対話]`（dialogue）の場合は verbosity を扱わないため、粒度の行は表示しない:

```
[対話] 答えを急がず、問いを重ねながら一緒に整理します
手法: ソクラテス式問答法 / GROWモデル
　　　→ 答えを提示せず、問いを重ねてご自身の考えを引き出す対話手法です（状況に応じてどちらかを使用）

このまま進めますか？ [yes / 別の方向で / 直接回答して / <別スキル名>]
```

WAIT_FOR: ユーザーの返答
- `yes` または Enter → 委譲する（上記共通定義の通り）
- `別の方向で` / `no` → 後述の「未分類の場合」と同じ一覧表示でスキルを選ばせる（WAIT_FORも同様）
- `直接回答して` → フレームを使わず `{input}` に対して直接回答する
- `<別スキル名>` → サブスキル一覧に存在するか確認する。存在しない場合は「スキル名 `<X>` は存在しません。使えるスキル: {サブスキル一覧テーブルの各行のスキル名をスラッシュ区切りで列挙したもの}」と伝えて再度選択を促す。存在する場合は委譲する

### 未分類の場合

いずれにも該当しない場合は以下を表示してユーザーに選択を求める。

```
どのスキルを使いますか？

{サブスキル一覧テーブルの各行を「- <スキル>（<カテゴリ>）: <説明>」の形式で、テーブルの順序どおりに列挙}

スキルを使わず直接回答することもできます。
```

WAIT_FOR: ユーザーの選択
- スキルを選んだ場合 → 委譲する（上記共通定義の通り）
- 直接回答を選んだ場合 → `{input}` に対して直接回答する

## 出力の整形・保存（verbosityが詳細相当の場合の共通フロー）

保存・共有用の資料としてまとめる必要がある場面（verbosity = 詳細、またはユーザーが「まとめて」「資料にして」などを明示した場合）は、各サブスキルの `templates/report.md` を使って保存する前に、以下の順で判断する。

1. 実行時に注入されている利用可能なスキル一覧を確認し、出力の形式・保存先の確認や整形・保存を担うスキルが存在するか照合する。
2. 該当しそうなスキルがあれば「〇〇（該当スキル名）で整形・保存しますか？（それともこのまま簡易テンプレートで進めますか？）」と一言確認する。
   WAIT_FOR: ユーザーの回答
   - 委譲する場合 → 分析結果・`{input}`・`{verbosity}` を渡してそのスキルに委譲する
   - 断られた場合 / 該当スキルが無い場合 → 以下の簡易保存フローに進む
3. 判定を無言で済ませず、必ずユーザーに確認してから進める。

IMPORTANT: 特定のスキル名をこの判定ロジックにハードコードしない。環境によって利用可能なスキル構成が異なるため、実行時の一覧と照合すること。

### 簡易保存フロー

「保存先のパスを教えてください（例: ~/Desktop）」と一言聞く。
WAIT_FOR: ユーザーの回答
ユーザーが答えたパスに対し:

1. Bash で `date +%Y%m%d-%H%M` を実行してファイル名用タイムスタンプを、`date +%Y-%m-%d` を実行してレポートタイトル用日付をそれぞれ取得する。ファイル名は `<スキル名>-<YYYYMMdd-HHmm>.md` とする
2. 指定パスが存在しない場合は Bash で `mkdir -p <path>` を実行してから保存する
3. Write ツールで保存する
4. Bash で `test -f <保存フルパス> && echo OK` を実行しファイルの存在を確認する。失敗した場合は Write を再試行する（最大1回）。

パスが省略されたり「ここ」「カレント」と言われた場合は `{SKILL_DIR}/`（= think/ 直下）に保存する。

PROHIBITED: ユーザーの保存先確認なしにファイルを書くこと。

## 連鎖モード

サブスキルの実行が完了した後、対話中にいつでも以下のコマンドで別スキルへ連鎖できる:

```
→ <スキル名>
```

例:
- `→ six-hats` — 出たアイデアをリスク・実現性の観点で検証する
- `→ triz` — 見えてきた矛盾・トレードオフを解消する
- `→ root-cause` — 前提・原因をもう一段掘り下げる
- `→ decide` — 出た案の中から選ぶ
- `→ idea` — 評価フェーズから発想フェーズに戻る
- `→ structure` — 話を整理して伝わる形にする
- `→ reflect` — ここまでの流れを振り返る
- `→ dialogue` — 答えを急がず、問いを重ねながら整理し直す

連鎖時は直前の `{input}` と会話文脈を引き継ぎ、`{verbosity}` と `{verbosity_label}` はそのまま維持する。
dialogue から他スキルへ連鎖する場合、`{input}` は dialogue 開始時の元の曖昧な入力ではなく、対話を通じて言語化された結論・整理内容を使うこと。dialogue は `{verbosity}` を扱わないが、dialogue に委譲する直前（ステップ1またはステップ2）で判定済みの `{verbosity}` の値を保持しておき、連鎖時にそれをそのまま使う。
スキル名が存在しない場合は「スキル名 `<X>` は存在しません。使えるスキル: {サブスキル一覧テーブルの各行のスキル名をスラッシュ区切りで列挙したもの}」と返して連鎖を中断する。
スキル名は存在するが SKILL.md の READ に失敗した場合は「スキル `<X>` を起動できません」と伝えて連鎖を中断する。
